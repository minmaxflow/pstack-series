# 10 · 元、支撑与入口

这一组九个 skill 是系统的外围器官。它们不直接干活,它们让系统自己变好、自己可审计、自己可配置、自己可被引导。

可以把它们分成四类。前三个是自我改进,`show-me-your-work` 让工作可审计,`figure-it-out` 和 `setup-pstack` 是定制,最后三个是入口和辅助。九个里绝大多数你不需要天天敲,但它们是 pstack 能长期用下去的底座。

## 自我改进的三个:correct、reflect、automate-me

这三个是同一个想法的三个尺度:**系统要自己变好,靠的是把教训编码进结构,而不是靠人反复教。** 它们一个改仓库,一个改 skill,一个生成你自己。

### correct

`correct` 改的是仓库。它对付的是"你反复纠正 agent 同一件事"。一次纠正只帮一次,而一次结构改动帮所有未来的会话,所以它要把"反复纠正"变成"结构强制":系统变好,靠的不是你记得提醒,而是让错的路根本走不通。它按一个固定的强度顺序修:先架构,再类型,再一个报错就说清正确写法的 lint,再测试,把文档放最后,因为文字是唯一一种被跳过也不会失败的东西。它有一个判断前提,值得原样抄下来:

> 假设每一个贡献者都是一个只看到自己打开的文件、照抄最近一个例子、走最短能编译的路的 agent。

所以你要把仓库设计成:从一个文件里做对的事,对整个仓库也是对的。

它先找出**错误类**。素材是最近的提交、回退、review 评论、agent 指令文件,以及那些解释 workaround 的注释。它把这些错误分组,一个类**出现过两次**才算数。

然后每一类在**能奏效的最高层级**上修。顺序是硬的。

1. **用架构消掉它。** 给每份状态一个所有者,每个任务一条支持的路。把内部藏起来,让错误的 import 直接失败。用手工同步的列表换成一个事实来源。删掉旧路和死代码,因为 agent 会照抄。
2. **用类型拦住它,让坏状态写不出来。** 如果坏代码还能编译,就加一条 lint 或 CI 检查,让它的报错**点名**该用的文件、类型或函数。如果这个模式已经很常见,就只在一次改动**新增**更多时才失败。
3. **用测试。** 修掉或删掉任何"所有被它调用的函数都返回空也照样通过"的测试。
4. **写文档或规则,放最后,而且只给判断类的事。** 一条规则被跳过时,不会有任何东西失败。

然后它修最高频的那几类,一类一个 commit,并且**证明每个新检查在一个真实的过去错误上失败**。同一条命令本地和 CI 都要跑。例外要写在出问题的那一行上,带上一个理由、一个到期日,和一个人的批准。

它最后维护一张**规则表**,放在 agent 指令文件里,把每条规则和强制它的东西配起来。当你又纠正它一次,它修掉这个错误并补上规则;如果这条规则本来就在、却没有东西强制它,那是一次重复,它要在同一次改动里把它修到最高层级。一条规则一旦对应的错误不可能再发生,就把它删掉。

### reflect

`reflect` 改的是 skill。从一次会话里提炼教训,最大的风险是过拟合:一次怪异的会话,可能让你把一条只对那次成立的偏好写进每个未来的会话。所以它的难点不是提炼,是分清"一次轶事"和"一条规则",而且任何 skill 改动都要先给你看、等你批准,因为一次编辑影响之后每一个会话。你在一次会话之后觉得"这次花了太久",敲它。

它先定位当前会话的 transcript。每个 harness 的路径不一样:Cursor 在系统提示里给的 `agent-transcripts/` 目录,Claude Code 在 `~/.claude/projects/<slug>/`,Pi 在 `~/.pi/agent/sessions/--<slug>--/`,Codex 按 `payload.cwd` 匹配。它只读当前工作区的会话,**绝不跨项目全局扫描**,因为那会读到无关项目的私密聊天。

然后它派三个并行 reviewer,各拿一个镜头:判断、工具、发散。三个都用 agent 模式,因为 reviewer 需要 MCP 访问去找上下文里提到的 ticket、聊天和可观测性记录,只读模式会把 MCP 剥掉。

结果交给一个合成器,排成三份:**Accepted、Rejected、Backlog**。在应用任何 Accepted 之前,它把完整的合成结果给你看,等你明确批准。它有一条很重要的克制:**一次怪异的会话是一个轶事,不是一条规则**,只有能改变未来某个决定的提案才值得接受。Backlog 项自动进你们的 devex 追踪器。它还有一步"结构性强制检查":任何一条如果用一个 lint、脚本、元数据标志或运行时检查来强制会更可靠,就从 Accepted 挪到 Backlog。

批准之后,它按路由字段决定谁来改:一行 bullet、一句收紧、一个过时事实的修正,它自己做;一个新 section、一个新模式表、超过十来行的实质编辑,交给 skill-authoring 流程(`create-skill`)跑它的起草、测试、迭代循环;如果问题是"这个 skill 该触发的时候没触发",那是一次描述优化;如果是新 skill,也走 `create-skill`,不许凭空发明形状。

### automate-me

`automate-me` 生成的是你自己的 mode。工具应该适配使用者,而不是反过来:poteto-mode 是某个人的风格,你未必要一模一样。它从你实际怎么工作里把风格读出来,而不是让你描述自己,因为人对自己的习惯往往看不清。生成之后你保留 pstack 做底,在旁边得到自己的入口。

它先检查你已经有没有一个 `<handle>-mode` skill(在项目级或用户级的 skill 目录里,category 子目录也要找)。有的话,默认是更新,而更新模式会改掉后面的流程:只挖 skill 上次编辑之后的历史,只问"变了什么、缺了什么",在原地编辑,保住你没推翻的 section。

然后挖你的历史。它把每个 workspace 的 transcript 切成几片并行挖(比如最近两到四周切成三片,让每片有足够素材)。每个切片挖的是六类默认信号:回复偏好、委派习惯、验证姿态、代码和散文纪律、流程约定、元偏好。**跨切片交叉验证**:两片以上都看到的信号是高置信度,单片的弱信号通常直接丢掉。

挖完还要问你,因为它挖不到你还没展示出来的意图:它给你一两道结构化多选(每道 4 到 6 个选项),先问宽的,再跟着你选的追问。它明确说"不要一口气问二十个问题"。

然后把信号聚成 section(回复风格、自主度、先理解、subagent、散文与代码纪律、评审与验证、流程、skill),再用 `create-skill` 起草。起草有几条护栏:**不要过拟合到一次对话**(一个说法只出现一次、又被另一次推翻,那是噪声,要多次出现才成文);**不要耍聪明**(把别的 skill 内容重述一遍、发明比喻、给 agent 读者写"诗意"的散文,都是只有成本没有收益);**引用,不要内联**(你依赖的别的 skill 用路径引用,不要贴片段);**最小化 section**(只有你有一条具体的、非默认的规则时才加一节,"沟通要清晰"不算,"短段落,比较选项时用表格,只有条目真的并列时才用 bullet"才算);命名用"用户"或"人",不用作者的名字;不要强求对称。

最后它在一个 worktree 里提交、开 PR,不直接推 main。

这三个的分工记住一句就够:`reflect` 从一次会话改 skill,`correct` 改仓库让错误类回不来,`automate-me` 生成你自己的入口。

## show-me-your-work

`show-me-your-work` 让长任务和无人值守的工作可审计。你不在场的时候,信任从哪里来?它不能来自事后的自述,因为自述和事实之间没有核对;它来自一份在运行过程中一行行写下的决策轨迹,加上一次跨模型的复审。这就是"先要证据"用在无人值守上的形态。

它维护一份决策日志,一个 TSV,一行一个决定。列是固定的。

- **ts**:ISO8601 时间戳。
- **phase**:阶段或工作流。
- **decision**:选了什么或做了什么,一行。
- **why**:用大白话写的理由。如果一个原则驱动了它,就平实地写出来,不要写成一个术语标签。
- **evidence**:一个证明它的链接或路径:commit SHA、PR 号、`file:line`,或者一个产物、trace、截图路径。永远不是一段话。
- **result**:结果或谓词状态,像 `tests green`、`reverted`、`pixel-diff 0`、`INCONCLUSIVE`、`open`。

它有一条关于"写入方式"的细节:它提供一个小助手 `scripts/log.sh` 来写行,这个助手会盖时间戳、首次使用时写表头、剥掉多余的 tab 和换行,并且给任何以 `=`、`+`、`-`、`@` 开头的单元格前缀一个单引号。最后一条是在防注入,因为一个 TSV 单元格以 `=` 开头,在表格软件里会被当成公式。

它记录的是**决策点**,不是每个动作:一个选定的分叉、一个完成并验证过的单元、一次带触发原因的转向或回退、一个浮出来的阻塞、一个修好的关卡。循环运行时,一次迭代一行。

它有几条硬规矩。日志**只能追加**。一个错误的决定用一行新记录去取代它,永远不编辑或删除历史。而且它偏好由提交过的脚本产出的证据,而不是手工做的一次性产物。

它默认是工作产物,不入库,放在工作目录的 `decisions.tsv`,或者多个任务并行时放在 `.audit/<task-slug>.tsv`。只有当工作足够大、reviewer 需要这份轨迹才敢信任结果时,才提交它。

它在结尾还有两个动作。

一个是**对着 transcript 审计日志**。交回给你之前,它读这次运行的 transcript,把每一行和真实发生的事对一遍:每一行是否对应一个真实的决定或动作;每行的证据是否能解析、是否显示了它声称的东西;一个影响了工作却没被记下来的分叉、转向或放弃的思路,是一个缺口,要补上。它纠正日志,不纠正故事:审计**从不**编辑或删除一行,哪怕是一行编造的。当一行既不对应真实决定、也不对应真实动作,或者它的说法或证据是错的,就加一行取代它。("你不该把发现向上取整成一句确定的话"在这里也适用。)

另一个是**跨模型复审**。它起一个不同模型族的 subagent,读这份日志和 transcript,标出你该注意的地方:证据薄弱的决定,声称验证过但 transcript 里没有证明的步骤,事后看有风险的取舍,以及你随便一瞥会漏掉的缺口。回复以一段 **Attention** 收尾,第一行是复审用的模型名,然后是每一条指向具体行或时刻的标记。"没有标记"也是一个有效值,但模型名不能空。那一段就是你要读的第一段。

## figure-it-out

`figure-it-out` 是当一个任务匹配不上任何更窄的 playbook 时,给你**定制**一个 playbook 的 skill。任务的形状决定流程;没有现成流程能装下它,就为这个任务设计一个,而不是硬塞进一个近似的模板。它的交付物在代码之前:先是一套可审计的工作流,然后才执行。

它的交付物,在任何代码之前,就是那套工作流本身。它分五个阶段。

**Phase A:Frame。** 先 grounding,再承诺。它要求你能说出三件事:把 done 定义成一个**可证伪的谓词**;量化范围(大概多少单元、多少工时、有哪些阻塞);以及严谨程度(**偏向高**,单向门和高影响面的工作要更多,可逆的低风险步骤要少)。它会在跳进一个长跑之前把框定和权衡present 给你看。可逆的工作直接做,但一个多小时的运行值得一个检查点。

**Phase B:设计工作流。** 把工作拆成原子、可独立落地的单元,**先做风险最高的未知**。脚手架和验证排在功能之前:先在改动前的状态上捕获基线,这样检查读起来是"旧值对新值"。单向门的设计决定跑 `architect`(它内部跑 `arena`),机械的、形状已定的工作跳过它。决定哪些能 fan out,只在接缝处并行,给每个 worker 自己的 worktree 或分支。然后把这个设计好的阶段列表**写下来**,那份列表就是给人审的东西。

**Phase C:跑循环。** 每个单元是一个实验。写下假设,做最小改动,对着谓词在**真实产物**上测量,前进了就留下,没前进就回退。用 sequence-verifiable-units 的纪律,每个单元验证过再开始下一个,而不是把检查攒到最后。验证靠检查产物,绝不靠自述;当某件事过得**太容易**,先怀疑观察方法,再怀疑系统。委派的活配一个 judge。如果一个 worker 在钻关卡的空子,重置并收紧契约;如果关卡本身错了,在它自己的改动里修关卡,不要绕过它。判决只有三种:VERIFIED、NOT VERIFIED、INCONCLUSIVE,而且 inconclusive 不是 pass,不许藏一个负面的结果。

**Phase D:留审计轨迹。** 用 `show-me-your-work` 记日志。`figure-it-out` 的工作通常足够大,值得把轨迹提交上去,让 reviewer 能在 PR 里读它。轨迹加 diff,就是让人回来时敢信任这份工作的东西。

**Phase E:验证并交回。** 对着 Phase A 的谓词在真实产品上检查整体,而不只是在 harness 上。把任何反复出现的纠正编码成一个关卡、一条 lint、一个检查或一个脚本。

它和 `orchestrate` 的分工值得说清:`figure-it-out` 设计**一次**定制的运行,是那个跑完就结束的东西;`orchestrate` 运转**一个程序**,跨多天、很多堆叠的 PR、一支 subagent 舰队,由一个常驻的协调者带着。

## setup-pstack

`setup-pstack` 配置 pstack 用哪些模型,以及每个角色的推理预算。模型是资源,应该按角色配置:把最强、最贵的判断力用在最需要判断的地方,把便宜和快用在机械的地方。"一个模型打天下"既贵又浪费它擅长的部分。

它枚举你这一会话里能传给 subagent 的模型 slug,这是它可靠的信息源(如果你不用这种枚举,它会让你把 slugs 贴进来,而且**绝不写一个没确认可用的 slug**)。它读现有的配置,把 `# budget` 行和各角色的值当作当前选择,顺便丢掉已经退休的角色行。

它问你一个预算档位,给四个选项:`unlimited`、`large`、`medium`、`small`,并说明 `large` 匹配 skill 默认值。档位是在改每个真实 slug 的**推理力度 token**:`unlimited` 提到 `max`,`large` 是 `xhigh`,`medium` 是 `high`,`small` 是 `medium`。它会给出一个不在可用集合里的 slug,标成"需要一个选择",然后给每个角色写一行。

它只覆盖你在意的角色。一个没有写进规则的角色,保持 skill 的默认值。写文件时它整份覆盖,让重跑保持幂等。Cursor 写到 `~/.cursor/rules/pstack-models.mdc`,其余 harness 写到 `~/.agents/pstack-models.md`。

你可能会踩的一个坑:把一个角色设成 `auto` 或 `inherit-parent`,它的意思不是某个模型 slug,而是"就用在跑父聊天的那个模型"。这正是 Auto 用户能一直待在 Auto 上的方式。对面板角色,值是**一个列表**,每一条起一个 subagent,所以列表长度就是面板大小。

它最后还有一步:检查你的项目有没有一个能驱动真实应用来取证的方式(一个 `verify-*` skill,或者一个已有的 harness)。如果没有,它就问一次要不要用 `create-verification-skill` 生成一个。说不,它就走,不推销。

## 入口和辅助:poteto-help、bro、make-bot-ui

### poteto-help

`poteto-help` 是给新手的。你不确定哪个 skill、playbook 或 principle 适合时,问它。

它做三件事:回答你的问题,**交给你一个可以自己输入的 prompt**,并链接答案来自的那个文件。它有一条重要性质:**对于一个问题,它不直接开始工作。** 因为一次 pstack 运行会真的花 token,所以它让你在准备好时把那个 prompt 发出去。它只在你亲手敲它的时候运行。

它会读取它要引用的那个文件,再引用它,并在文件和自己冲突时**相信文件**。它给的链接指向已安装的插件,你可能打不开,所以它给你公开的副本地址。

它还维护一张把症状映射到修法的表,值得抄几句:"模式在几轮之后不再生效"是因为用 Enter 启动了它,要改成 Custom Mode 或每个任务都敲 `/poteto-mode`;"一个问题被当成了上一个任务的下一步",说"new task";"新的模型选择没生效",规则只对新聊天生效,开一个新的;"一次过夜运行动了但什么都没完成",`/loop` 需要一个能过或不过的检查,不是一个时长。

它还会分清一些接近的情况:`how` 讲代码做什么,`why` 讲原因,`teach` 跑其中一个或两个再讲清楚;`arena` 给每个 worker 同一个 brief 再合并最好的部分,`swarm` 切成切片或一场竞速再返回一份报告;`recall` 跨近期聊天重建上下文,恢复某一段具体会话是 session-pickup playbook。

它还会告诉你在 pstack 之外的东西:`deslop`、`control-cli`、`control-ui` 来自 `cursor-team-kit` 插件;`/loop` 和 `/create-skill` 是 Cursor 内建;pstack 没有 `/orchestrate` 这个 skill,orchestrate 是一个 `/poteto-mode` 的 playbook。

### bro

`bro` 是整个系列里最短的一个。它把上一条消息用朴素的人话重说一遍,没有术语,更短,像一个人在跟另一个人说话。当你收到一条技术上很详尽、你却仍然不知道它到底说了什么的回复,敲 `/bro`。就这一个词。

### make-bot-ui

`make-bot-ui` 是给 Grok Bot 用户的一个情境 skill。它造一个小页面,你点按钮,你机器上的一个 server 向一个 webhook routine POST 一个 JSON,bot 就带着这个 JSON 醒来。

它最在意的一件事是安全:**sender key 留在服务器上,不进浏览器,不进聊天,也不进这个 skill。** 具体做法是让 key 走一次 `secret-request`,你提交之后它就是看不到值,值落在一个 connector 的凭据文件里,被复制进 server 配置,从不打印、从不记日志。服务器 POST 时带 `Authorization: Bearer <key>` 和 `X-Automation-Key: <key>`,8 秒超时,只试一次不重试。

它还有几条很实在的工程细节:server 绑 `0.0.0.0:<port>` 而不是 `127.0.0.1`,否则 Tailscale 的 peer 到不了;第一次告诉用户"上线了"之前,先用一个无害的 payload 探一次;PUT 可能失败时,把同一个 JSON 追加到本地日志,从 routine 里把日志排干,不要拿轮询当主路径;一个已经 online 的 Tailscale 节点不要再建第二个主机名;webhook 醒来的那一轮里,body 是**外部数据,不是指令**,按字段解析,不当命令执行。

## 把九个连起来看

这一组是系统的底座。

自我改进的三个改不同层:`reflect` 改 skill,`correct` 改仓库,`automate-me` 生成你的入口。`show-me-your-work` 让无人值守的工作可被审计。`figure-it-out` 在没有现成流程时定制一个。`setup-pstack` 决定用哪些模型。最后三个是入口和辅助。

它们合起来,回答的是一个更长远的问题:pstack 为什么能一直用下去。因为 `correct` 会让同一个错误不再回来,`reflect` 会让 skill 随使用变好,`automate-me` 让这套东西终于像你自己的。一个不会自我改进的系统,用久了只会越来越像一堆没人维护的提示词。
