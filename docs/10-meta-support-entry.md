# 10 · 元、支撑与入口

这一组九个 skill 是系统的外围器官。它们不直接干活,它们让系统自己变好、自己可审计、自己可配置、自己可被引导。

可以把它们分成四类。前三个是自我改进,`show-me-your-work` 让工作可审计,`figure-it-out` 和 `setup-pstack` 是定制,最后三个是入口和辅助。九个里绝大多数你不需要天天敲,但它们是 pstack 能长期用下去的底座。

## 自我改进的三个:correct、reflect、automate-me

这三个改的东西不一样,一个改仓库,一个改 skill,一个生成你自己。

`correct` 改的是仓库。它对付的是"你反复纠正 agent 同一件事"。它的判断前提很值得抄下来:**假设每一个贡献者都是一个只看到自己打开的文件、照抄最近一个例子、走最短能编译的路的 agent。** 所以你要把仓库设计成:从一个文件里做对的事,对整个仓库也是对的。

它先找出错误类,一个类出现过两次就算数。然后每一类在**能奏效的最高层级**上修,顺序是硬的:先想办法用架构消掉它,让错误的路干脆写不出来;再用类型,让坏状态无法表达;不行就加一条报错就说出正确写法的 lint 或 CI 检查;再不行才写测试;文档和规则放最后,因为一条规则被跳过时,不会有任何东西失败。它要求每个新检查在一个真实的过去错误上失败,证明自己有用。它还在 agent 指令文件里维护一张表,把每条规则和强制它的东西配对,没有强制者的规则会以重复的形式露出来。

`reflect` 改的是 skill。你在一次会话之后觉得"这次花了太久",敲它。它把这次会话的 transcript 交给三个并行 reviewer,分别用判断、工具、发散三个视角看,然后一个 synthesizer 把提案排成 Accepted、Rejected、Backlog,等你批准。它在批准之前不改任何 skill。它有一条很重要的克制:**一次怪异的会话是一个轶事,不是一条规则。** 只有能改变未来某个决定的提案才值得接受。

`automate-me` 生成的是你自己的 mode。它从你最近的历史里读出你的风格,在你如何要回复、如何委派、如何验证、如何写代码、如何写 prose、如何处理流程上,找出重复出现的偏好,再问哪些真的是你。它草拟一个 `<你的名字>-mode` skill,过一遍 `unslop`,从一个 worktree 开一个 PR,让你像审查任何改动一样审查它。再跑一次,它只挖上次编辑之后的历史,保留你没推翻的规则,有证据的就改,真正新的模式才加。它不替换 pstack,你在它底下保留 pstack 做底,在旁边得到自己的路由 skill。

这三个的分工记住一句就够:`reflect` 从一次会话改 skill,`correct` 改仓库让错误类回不来,`automate-me` 生成你自己的入口。

## show-me-your-work

`show-me-your-work` 让长任务和无人值守的工作可审计。

它维护一份决策日志,一个 TSV,一行一个决定。列是固定的:时间、阶段、决定(一句话)、为什么(大白话,如果一个原则驱动了它,就平实地写出来,不要写成一个术语标签)、证据(一个链接或路径,不是一段话)、结果。

它默认是工作产物,不入库。只有当工作足够大、reviewer 需要这份轨迹才敢信任结果时,才提交它。什么时候提交,什么时候留在本地,这个判断本身就是它的一部分。

日志有几条硬规矩。只能追加。一个错误的决定用一行新记录去取代它,永远不编辑或删除历史。

它在结尾还有一个动作。交回给你之前,它会起一个不同模型族的 subagent,读这份日志和这次运行的 transcript,标出你该注意的地方:证据薄弱的决定,声称验证过但 transcript 里没有证明的步骤,事后看有风险的取舍。回复以一段 Attention 收尾,而那一段就是你要读的第一段。你在审计决定,不是在重读一整夜。

## figure-it-out

`figure-it-out` 是当一个任务匹配不上任何更窄的 playbook 时,给你**定制**一个 playbook 的 skill。

它的交付物,在任何代码之前,就是那套工作流本身。它先框定:把 done 定义成一个可证伪的谓词,把范围量化(大概多少单元、多少工时、有哪些阻塞),再定严谨程度,并且偏向高。然后设计工作流:把工作拆成原子、可独立落地的单元,先做风险最高的未知,验证 harness 和脚手架排在功能之前,harness 还要从改动前的状态捕获基线,这样检查读起来是"旧值对新值"。

它进入一个循环,每个单元是一个实验:写下假设,做最小改动,对着谓词在真实产物上测量,前进了就留下,没前进就回退。判决只有三种:VERIFIED、NOT VERIFIED、INCONCLUSIVE,而且 inconclusive 不是 pass。它把整条轨迹写进决策日志。

它和 `orchestrate` 的分工值得说清。`figure-it-out` 设计**一次**定制的运行,是那个跑完就结束的东西。`orchestrate` 是运转**一个程序**:跨多天、很多堆叠的 PR、一支 subagent 舰队,由一个常驻的协调者带着。

## setup-pstack

`setup-pstack` 配置 pstack 用哪些模型,以及每个角色的推理预算。

它枚举你这一会话里能传给 subagent 的模型 slug,问你一个预算档位,然后给每个角色写一份配置:Cursor 里写到 `~/.cursor/rules/pstack-models.mdc`,其他 harness 写到 `~/.agents/pstack-models.md`。编码、判断、各个 review panel,每个角色一行。

它只覆盖你在意的角色。一个没有写进规则的角色的,保持 skill 的默认值。

你可能会踩的一个坑:把一个角色设成 `auto` 或 `inherit-parent`,它的意思不是某个模型 slug,而是"就用在跑父聊天的那个模型"。这正是 Auto 用户能一直待在 Auto 上的方式。

## 入口和辅助:poteto-help、bro、make-bot-ui

`poteto-help` 是给新手的。你不确定哪个 skill、playbook 或 principle 适合时,问它。它弄清你到底想做什么,回答那一部分,然后交给你一个可以自己输入的 prompt,外加答案的来源链接。它不会直接开始工作,因为一次 pstack 运行会真的花 token,那个 prompt 由你在准备好时发出去。它只在你亲手敲它的时候运行。

`bro` 是整个系列里最短的一个。它把上一条消息用朴素的人话重说一遍,没有术语,更短。当你收到一条技术上很详尽、你却仍然不知道它到底说了什么的回复,敲 `/bro`。就这一个词。

`make-bot-ui` 是给 Grok Bot 用户的一个情境 skill。它造一个小页面,按钮通过一个 webhook routine 唤醒 bot。比如你可以滑一个 review 队列,每一次滑动就请 bot 对那一条动手。你机器上的一个 server 拿着 webhook 的 sender key,所以 key 不会到浏览器或者聊天里。它也管把页面暴露到 Tailscale 上。

## 把九个连起来看

这一组是系统的底座。

自我改进的三个改不同层:`reflect` 改 skill,`correct` 改仓库,`automate-me` 生成你的入口。`show-me-your-work` 让无人值守的工作可被审计。`figure-it-out` 在没有现成流程时定制一个。`setup-pstack` 决定用哪些模型。最后三个是入口和辅助。

它们合起来,回答的是一个更长远的问题:pstack 为什么能一直用下去。因为 `correct` 会让同一个错误不再回来,`reflect` 会让 skill 随使用变好,`automate-me` 让这套东西终于像你自己的。一个不会自我改进的系统,用久了只会越来越像一堆没人维护的提示词。

## 今天就做一件事

在你的仓库里跑一次 `correct`,选一个你已经纠正过两次的错误类。看看能不能把它从"写在 prompt 里的一句话"升级成一个"跳过了就会失败"的结构。
