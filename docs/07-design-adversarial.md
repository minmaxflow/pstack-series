# 07 · 设计与对抗

一次尝试,会锁死模型想到的第一个形状。

这不是模型的缺陷,是它的工作方式。你让它设计一个方案,它给出一个,看起来合理,你就用了。三个月后你发现,另一个方案本来能省掉一半代码。

这一组四个 skill 都在对抗这件事。它们用两种武器:**并行**(同时产生多个答案)和**模型差异**(让不同的模型互相挑错)。

## architect

`architect` 在写代码之前,先把类型、函数签名、类形状、模块边界画出来,用 `not implemented` 的函数体和伪代码。这些草图先在多个模型视角之间综合,然后在选定的草图上把代码填进去。如果实现证明草图是错的,就把草图扔掉重来。

它有一个五阶段的循环。

**Ground。** 先把新代码触碰到的每一个系统建立真实模型,跑 `how`。如果设计重新定义了所有权或分层,再加 `why`,让已有的理由变成约束,而不是猜测。只有真正从零开始、周围没有系统可整合时,才跳过这一步。

**Sketch。** 跑 `arena`,要求至少两个**结构上不同**的候选,哪怕第一个看起来就够用。这是 exhaust-the-design-space 原则的具体化,要的是整体形状的备选,不是同一个形状里的点修。每个候选都要过一遍设计红线清单,清单的假设写得很实在:下一个贡献者是一个 agent,它只看到自己打开的文件,照抄最近的一个例子,走最短的能编译的路。所以在两个候选之间,选那个"从一个文件里做对的事,对整个仓库也对"的设计。

**Agree。** 默认不设检查点,直接从合成出来的设计进入实现。只有调用方明确要求("先给我看再实现")时才停下来等人签收。

**Implement。** 用草图当契约,把 `not implemented` 换成代码。偏离草图是要浮出来的信号,不是要默默吸收的摩擦。如果一个函数需要一个草图没预料到的参数,回来问:是草图错了,是需求漏了,还是实现越界了。

**Scrap。** 这是最容易被跳过、也最重要的一步。如果实现持续产生草图吸收不了的摩擦,就把草图扔掉,不要往上打补丁。信号是一个模式,不是单个例子:同一种 workaround 在不相干的代码里反复出现;多个不相干的边界情况都需要特殊分支;类型需要逃生舱(`any`、cast、实际上总会被赋值的可选字段)才能编译;草图说状态不共享,实现里却本能地想要一把锁;调用方必须知道抽象的内部规则才能用它。

它的输出有一条固定纪律:**调用方的用法先写,类型从用法里派生出来。** 小改动是一份新类型和签名,大改动是模块图加类型定义,再附一份 rationale,里面记下合成决定。

## arena

`arena` 对同一个任务并行起 N 个候选,读完每一个,选最强的做底,再把其他候选里最好的想法嫁接进来,验证合成结果。

它的阶段是这些。

**Frame。** N 个候选会收到同一个 prompt,所以这个 prompt 就是契约。先声明每个候选要产出什么,再从"这个任务的成功长什么样"里推导出三到六条可打分的标准,这个 rubric 是挑选工具,候选看不到它。每个候选写到自己的位置,一个 worktree,或者 `/tmp/arena-<slug>/candidate-<n>/`。这一步是 separate-before-serializing-shared-state 的直接应用。

**Fan out。** 一次消息里并发起全部候选。

**Cross-judge。** 全部候选完成后,在**不同模型族**上起一个只读的 judge,它看到 rubric 和打了标签的候选,逐条打分,推荐一个底。它和你的阅读并行,但不要和候选并行,候选还在写的时候不要起 judge。

**Pick a base。** 读完每一个候选,逐条对着 rubric 打分,不靠整体感觉。挑那个"未来的维护者最容易在不破坏不变式的前提下扩展"的候选。两个打平时,偏好边界更干净、API 更小的那个。

**Graft。** 再走一遍每个落选的候选,找出值得移植进来的东西。信号通常是一个候选一两样,不是大半。手工融合,不要机械粘贴,结果必须在一个心智模型下保持连贯。

**Verify。** 合成出来的产物要像任何其他产出一样接受审查。

它有两个很有用的观察。候选们收敛到同一个形状,是强一致信号,直接发共识形状,不用嫁接。候选们疯狂发散,说明 Frame 阶段规格没写清,重新框定再跑一次,不要把它们平均掉。

## swarm

`swarm` 把 N 个 worker 铺开,它们可以覆盖互不相同的切片、覆盖矩阵、gauntlet lane、探索分区,或者声明的竞速臂。每个 worker 有自己的范围和检查,回报 `PASS`、`ISSUES` 或 `BLOCKED`。父进程等所有人回来,只返回一份紧凑报告,不复读原始输出。

它和 arena 的区别要记住,用错会浪费。

`arena` 给每个 worker 同一个 brief,然后选底、嫁接。`swarm` 覆盖切片,或者跑一场"选择规则事先声明"的竞速。它不做选底和嫁接那一套仪式。

竞速的规则必须在发出去之前就声明:先到先得、全部排名,还是取最好。事后才知道要按什么选,那场竞速就没有意义。

每个 brief 都要能独立成立:目标、范围、确切的切片或竞速臂、怎么验证、回报什么。测量类的 brief 还要写明方法(采样数、一个样本是什么、顺序),worker 把它记进结果。

## interrogate

`interrogate` 把同一份 diff、意图和 rubric 发给不同模型族上的 reviewer,让它们从各自的角度挑战这份改动。

它的核心机制是一句反直觉的话:**对抗信号来自模型差异,不是来自指定的人设。** 你不需要给 reviewer A 安一个"安全专家"的角色,你只需要让它和 reviewer B 是不同的模型。不同模型有不同的盲区,两个模型各自独立提出的发现,是最高置信度的信号。

拿到结果后,你自己是 lead,是一个务实的资深工程师,不是中立的汇总器。把每条发现分进四个桶:Act on(真的影响正确性、安全或可维护性,会挡住一个真实 PR)、Consider(合理,但不确定现在值不值得处理)、Noted(有效但不可行动)、Dismissed(错的、挑刺的,或者缺少上下文,给一句简短理由)。每条都要标明是哪些模型提出的。**不要自动应用任何改动。**

这里有一条重要的使用边界。`interrogate` 要用在 diff 上。你把对抗性审查指向一个还没有代码支撑的计划,reviewer 会凭空发明永远不会发生的风险和边界情况。先用原型把开放问题解决掉,再审查做出来的东西。

## 把四个连起来看

这四个是两种不同的并行,加一个元 skill。

`architect` 是"先定形"的元 skill,它内部会调用 `arena`。`arena` 是"同题多解、选底、嫁接"。`swarm` 是"切片覆盖或竞速"。`interrogate` 是"多模型对抗审查一个已有产物"。

它们的共同点,是用并行和模型差异去对冲单个模型第一个想到的形状。它们的判断锚点是**模型多样性**,不是"某个模型更聪明"。

边界也要说清。设计或代码的 bake-off 用 `arena`,每个 worker 拿同一个 brief;覆盖和竞速用 `swarm`。审查一份 diff 用 `interrogate`,审查一个抽象计划是浪费。

## 今天就做的一件事

面对一个没有先例、又难以反悔的设计,先做两三个**结构上不同**的原型,再选。注意是结构上不同,同一个思路的两种写法不算,那只是确认你已经想到的东西。
