# 07 · 设计与对抗

一次尝试,会锁死模型想到的第一个形状。

这不是模型的缺陷,是它的工作方式。你让它设计一个方案,它给出一个,看起来合理,你就用了。三个月后你发现,另一个方案本来能省掉一半代码。

这一组四个 skill 都在对抗这件事。它们用两种武器:**并行**(同时产生多个答案)和**模型差异**(让不同的模型互相挑错)。

## architect

设计一旦写进代码就很难反悔,所以它的价值在于它是唯一便宜的反悔窗口:在写实现之前把形状先摆出来,而且刻意做两个结构上不同的版本,让选错的风险在代价最低的时候暴露。

`architect` 在写代码之前,先把类型、函数签名、类形状、模块边界画出来,用 `not implemented` 的函数体和伪代码。这些草图先在多个模型视角之间综合,然后在选定的草图上把代码填进去。如果实现证明草图是错的,就把草图扔掉重来。

它有一个五阶段的循环,每个阶段都有明确的进入和退出条件。

**Phase A: Ground。** 先给新代码触碰到的每一个系统建立真实模型,跑 `how`。如果设计重新定义了所有权或分层,再加 `why`,让已有的理由变成约束,而不是猜测。

这里有一句判据:**命名一个文件不叫 grounding。** 你要产出 `how` 规定的那份被追踪过的模型。只有真正从零开始、周围没有系统可整合时,才跳过这一步。

**Phase B: Sketch。** 它跑 `arena`,把设计任务和 Phase A 的 grounding 产物一起交出去。每个候选拿到一份 runner prompt,产出一个按 rationale 模板组织的设计包。

它要求**至少两个结构上不同的候选**,哪怕第一个看起来就够用。这是 exhaust-the-design-space 原则的具体化,要的是整体形状的备选,不是同一个形状里的点修。

候选在合成之前要先过一遍**设计红线清单**。这份清单的假设写得很实在:下一个贡献者是一个 agent,它只看到自己打开的文件,照抄最近的一个例子,走最短的能编译的路。所以在两个候选之间,选那个"从一个文件里做对的事,对整个仓库也对"的设计。

比较候选的轴是**接口深度**:优先那个把更多复杂度藏在更小的公共面后面的设计。一个很厚的接口,如果它把能力集中起来、让调用链保持短,这是好事;一个很宽的接口,如果它藏不住复杂度,那是坏事。

**Phase C: Agree。** 默认不设检查点,直接从合成出来的设计进入实现。只有调用方明确要求("先给我看再实现")时才停下来等你签收。如果你在检查点里对形状提出异议,它把这当成 Phase A 的证据,回到 Phase B 重跑。

**Phase D: Implement。** 用草图当契约,把 `not implemented` 换成代码,把伪代码换成逻辑。**偏离草图是要浮出来的信号,不是要默默吸收的摩擦。** 如果一个函数需要一个草图没预料到的参数,回来问:是草图错了,是需求漏了,还是实现越界了。

**Phase E: Scrap。** 这是最容易被跳过、也最重要的一步。如果实现持续产生草图吸收不了的摩擦,就把草图扔掉,不要往上打补丁。

它判断信号看的是一个**模式,不是单个例子**。它列出的征兆很具体:同一种 workaround 在不相干的代码里反复出现;多个不相干的边界情况都需要特殊分支;类型需要逃生舱(`any`、cast、实际上总会被赋值的可选字段)才能编译;草图说状态不共享,实现里却本能地想要一把锁;调用方必须知道抽象的内部规则才能用它;以及 Phase D 里出现了两个或以上同形状的偏离。

推翻的时候不是重来一遍了事。它按固定顺序做:先用 `how` 重新理解已经建出来的东西,再按新约束重画(redesign-from-first-principles),再先减后加,让新草图比旧草图更小,然后回到 Phase B 重跑 `arena`。

它的输出有一条固定纪律:**调用方的用法先写,类型从用法里派生出来。** 小改动是一份新类型和签名,大改动是模块图加类型定义,再附一份 rationale,里面记下用法草图和合成决定。

## arena

同一个问题,不同的模型会想到不同的形状,也带着不同的盲区。让多个候选同时上场、互相取长补短,得到的不是平均,而是一个比任何单个候选都更强的合成:选一个做底,再把别人身上最好的那一小部分嫁接进来。

`arena` 对同一个任务并行起 N 个候选,读完每一个,选最强的做底,再把其他候选里最好的想法嫁接进来,验证合成结果。

它的阶段是这些。

**Phase A: Frame。** N 个候选会收到同一个 prompt,所以这个 prompt 就是契约。它先声明每个候选要产出什么,再从"这个任务的成功长什么样"里推导出**三到六条可打分的标准**。这个 rubric 是挑选工具,候选看不到它。

然后是分配输出位置。每个候选写到自己的地方:一个 git worktree,或者 `/tmp/arena-<slug>/candidate-<n>/`。这是 separate-before-serializing-shared-state 的直接应用,它保证 N 个候选不会互相覆盖。

**Phase B: Fan out。** 一次消息里并发起全部候选,后台运行。每个候选不只产出作品,还要产出一段简短的理由,写明它考虑过哪些备选、否决了什么。如果某个候选没产出东西,就带 N-1 个继续,并在合成记录里记下这个掉队的。

**Phase C: Cross-judge。** 全部候选完成后,在**不同模型族**上起一个只读的 judge。它看到 rubric 和按路径标签区分的候选,逐条打分,推荐一个底。它和你的阅读并行,但**不要**和候选并行:候选还在写的时候不要起 judge。

**Phase D: Pick a base。** 读完每一个候选,**逐条对着 rubric 打分,不靠整体感觉。** 挑那个"未来的维护者最容易在不破坏不变式的前提下扩展"的候选。两个打平时,偏好边界更干净、API 更小的那个(这是 laziness 在起作用)。它把你的判断和 cross-judge 的判断对比:一致就是确认,不一致说明有一方有偏见,或者 rubric 本身含糊,两边都要读。

**Phase E: Graft。** 再走一遍每个落选的候选,找出值得移植进来的东西。信号通常是**一个候选一两样,不是大半**。手工融合,不要机械粘贴,结果必须在一个心智模型下保持连贯。嫁接了什么、来自哪个候选、否决了什么、为什么,都要记录。

**Phase F: Verify。** 合成出来的产物要像任何其他产出一样接受审查。如果验证暴露了一个 arena 没抓到的问题,要么是 Phase A 错了(重新框定重跑),要么是某个候选抓到了但你漏了嫁接(回到 Phase E)。不要糊过去。

它有两个很有用的观察。候选们收敛到同一个形状,是**强一致信号**,直接发共识形状,不用嫁接。候选们疯狂发散,说明 Phase A 规格没写清,重新框定再跑一次,不要把它们平均掉。

它的输出是一份合成作品,加一份简短的合成记录:底是谁、嫁接了哪些(来自哪个候选)、否决了什么、有没有掉队的、验证结果如何。

## swarm

有些工作可以切成互不重叠的片,有些可以让几路同时跑、事先声明怎么选赢家。切开了就能并行覆盖,而且每一片都有自己的检查,父进程只收一份合并后的报告。它和 arena 的差别不在并行,在目的:arena 是同一个 brief 的多解,swarm 是**覆盖或赛跑**。

`swarm` 把 N 个 worker 铺开,它们可以覆盖互不相同的切片、覆盖矩阵、gauntlet lane、探索分区,或者声明的竞速臂。每个 worker 有自己的范围和检查,回报 `PASS`、`ISSUES` 或 `BLOCKED`。父进程等所有人回来,只返回一份紧凑报告。

它的阶段是四个。

**Phase A: Frame。** 先声明**完成谓词**和这次要返回的产物或报告。然后选形状:切成互不重叠的切片、让 N 个 worker 跑同一个 brief 竞速,还是两者混合。

如果是竞速或混合,必须在发出去之前就声明选择规则:先到先得、全部排名,还是取最好。事后才知道要按什么选,那场竞速就没有意义。

然后定 worker 模型,给每个 worker 一份自己的可写输出。**测量类的 brief 必须写明确切的 SHA 和方法**(采样数、一个样本是什么、顺序),worker 要把这两样都记进结果。

**Phase B: Fan out。** 默认用云端 worker,一次消息全部发出去,每个 worker 一台机器,从根上避免共享写。必须本地跑时才用本地。

**Phase C: Aggregate。** 读每个 worker 的结论。**一个没有记录 brief 里要求的 SHA 和方法的结果,直接丢掉,重派一次;第二次还没有,就记成一个缺口。而缺口不算通过。** 覆盖形状下,每一个必需的切片都要有结果。竞速形状下,套用事先声明的规则。**不要把 worker 的原始输出复制粘贴上来。**

**Phase D: Report。** 交回一份合并报告:一张紧凑的表,一行一条带证据的 issue,明确的缺口或掉队,以及竞速时用到的规则。

## interrogate

对抗信号来自模型差异,不是来自指定的人设。不同模型有不同的盲区,所以两个模型各自独立提出的发现,是最高置信度的信号;而同一个模型提出的、又和它自己生成的东西相关的判断,几乎没有信息。这正是"生成和评判分开"的一个具体形态。

`interrogate` 把同一份 diff、意图和 rubric 发给不同模型族上的 reviewer,让它们从各自的角度挑战这份改动。

它的步骤是这些。

**确定范围。** 你指了文件或 diff 就用那个;在功能分支上就跑 `git diff main...HEAD` 拿完整改动集;如果消息提到最近的工作,就把相关文件收集起来。它还要把理解这份代码所需的周边上下文一起打包。

**先明说意图。** 在派出任何 reviewer 之前,它把这次改动的意图写成一段话,来源是:你的消息、提交信息、PR 描述、以及代码本身。如果它不确定意图,它先问你。这一步是必要的,因为 reviewer 是在评判"这个改动有没有达到它想达到的目标",意图不清,评判就没有锚。

**派 reviewer。** 按配置好的模型列表,一个模型一个 reviewer,所有人拿到完全相同的 prompt:同一段意图、同一份 diff、同一套 rubric、同一个代码质量镜头。

**合成。** 把所有发现放在一起:共识(2 个以上模型独立提出)是最高信号;单独一个模型的发现仍然值得读,但权重要低;不同模型用不同方式描述同一个问题的,合并,并标出是哪些模型提的;一个模型报了什么、另一个明确说了相反的,这个分歧本身是好线索。

**你来当 lead。** 你是一个务实的资深工程师,不是中立的汇总器。把每条发现分进四个桶。

- **Act on**:真的影响正确性、安全或可维护性,会挡住一个真实 PR。
- **Consider**:合理,但不确定现在值不值得处理。
- **Noted**:有效但不可行动,比如依赖上下文、过早优化、当前阶段影响很小。
- **Dismissed**:错的、挑刺的,或者缺少上下文,给一句简短理由。

每条都要标明是哪些模型提出的,以及分到这个桶的原因。**它不自动应用任何改动。**

这里有一条重要的使用边界。`interrogate` 要用在 **diff** 上。你把对抗性审查指向一个还没有代码支撑的计划,reviewer 会凭空发明永远不会发生的风险和边界情况。先用原型把开放问题解决掉,再审查做出来的东西。

## 把四个连起来看

这四个是两种不同的并行,加一个元 skill。

`architect` 是"先定形"的元 skill,它内部会调用 `arena`。`arena` 是"同题多解、选底、嫁接"。`swarm` 是"切片覆盖或竞速"。`interrogate` 是"多模型对抗审查一个已有产物"。

它们的共同点,是用并行和模型差异去对冲单个模型第一个想到的形状。它们的判断锚点是**模型多样性**,不是"某个模型更聪明"。这也是为什么配置里那么多角色都是**一个模型列表**:面板的长度就是并行度,而且刻意让不同家族混在一起。

边界也要说清。设计或代码的 bake-off 用 `arena`,每个 worker 拿同一个 brief;覆盖和竞速用 `swarm`。审查一份 diff 用 `interrogate`,审查一个抽象计划是浪费。`architect` 默认一路做到实现,想先看设计就在 prompt 里加"with checkpoint"。

## 今天就做一件事

面对一个没有先例、又难以反悔的设计,先做两三个**结构上不同**的原型,再选。注意是结构上不同,同一个思路的两种写法不算,那只是确认你已经想到的东西。
