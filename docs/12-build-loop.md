# 12 · 构建循环

这一篇是"构建"这一大类的 playbook。它们共享一条纪律:**说清你观察到了什么,然后让 playbook 去要证据。**

你不需要把这些步骤全写进 prompt。你说症状,说完成条件,playbook 会补上你没打出来的那几步:修之前先复现,实现之前先命名数据形状,重构之前先钉住行为,优化之前先 profile。

## feature

`feature` 做新行为或改过的行为,从一个命名好的数据形状建起。

它的顺序是固定。先跑 `how` 摸清受影响的子系统,再跑 `architect` 做并行设计探索。然后写 throughput checkpoint,把它铺成四个 todo:哪些是阻塞性的第一步(必须在 fan-out 之前跑的关卡)、哪些是独立工作流(不相干的文件、服务、层可以并行,共享写要串行)、共享可变状态是什么(默认拆开写目标)、以及最小安全分解是什么(如果一个 worker 最好,说明为什么)。

然后是委派。它把写代码的任务交给一个 subagent,给一个具体的范围:文件路径、命名好的数据形状和它的组织方式、成功标准。当实现有多个合法形状时(错误处理、抽象层、测试结构),它改用 `arena` 委派,让多个 runner 把备选摆出来,让 cross-judge 守住挑选。

最后在匹配的 surface 上验证,rebase 成小而有顺序的 commit。

## refactoring

`refactoring` 是行为不变的结构改动。

它的第一件事不是动结构,是钉住行为契约。跑 `how` 学清楚现在的契约,然后写一个 characterization test、一个 snapshot,或者一个等价 harness,在任何结构移动之前把当前行为捕获下来。如果这块区域没有覆盖,就先把 pin 写出来再碰结构。类型检查和 lint 不算 pin。

然后是命名。命名代码缺失的那个结构,再命名目标形状(如果今天建,模块布局、类型、调用图应该是什么样),跨函数边界时先跑 `architect`。接着先减后加:删死代码、折叠单调用者包装、丢掉多余校验、清掉孤儿引用,再引入新形状。

移动要小步,每一步都保持 pin 绿。API 重塑的同一波里,迁移所有调用方,删掉旧 API,不要兼容垫片,不要新旧并存的路径。这里有一个容易漏的点:重命名会静默地在字符串、prose、反向引用里漏掉用法,所以每一次重命名都要对着真实文件抽查。

最后在真实产物上证明行为没变,而不是"能编译"。成功的标准是 reader load 降低了。如果这次 diff 没有在某处降低 reader load,就回退它。

还有一个例子,它教你怎么处理"顺手发现的问题":如果清理暴露出一个缺失功能或者一个真的 bug,把它拆出去,先把这次结构改完、发出去,再单独处理那个发现。

## bug-fix

`bug-fix` 的原则说得最直白:**你是这个任务的负责人。每一行上线的代码都能追溯到运行时证据。**

"可能有用"的双保险,只是一个假设,它不发。证据推翻了假设,就把促使它的那个改动一起回退。最小的、被证据支持的那个改动才上线,不多一行。

步骤是这些。先自己在匹配的 surface 上复现,即使某个调试协议让你去请用户复现。用二分法找原因:形成候选假设,一个个排除,直到只剩一个。每个候选由 `how` 给种子,回归史用 `why`。确认存活下来的**机制**有运行时证据,再进入规划。规划修复(跨函数边界先 `architect`),把实现委派给 subagent。然后在**同一个** surface 上验证,原始 repro 现在通过。`inconclusive` 或者错的 surface 不算通过,要标出来。最后让失败的 repro 先于修复进 git 历史,再开 PR。

那条"同一个 surface"值得强调。测试通过只说明分支行为,不说明 bug 消失。UI 的 bug 要在 UI 上复现和验证。

## perf-issue

`perf-issue` 追踪一个测量到的慢,对着基线改进。

它是一次性修复。这就是它和 `hillclimb` 的区别:那个是持续循环。它跑 `benchmark-checklist` 审自己的基线,以及之后每一个数字。顺序是先 profile,再优化**测量到的**原因,不是你先猜到的那一个。

## hillclimb

`hillclimb` 是对一个可测量的东西持续、科学地改进,对着一个目标。

它的核心纪律只有一句:**一个改动,一次测量,留或回退。** 永不堆叠未测的改动,永不从代码审查里宣称一个赢。

它先建测量 harness,证明它的敏感度,然后**冻结**它。冻结之前,用 `benchmark-checklist` 审一遍。harness 要打印它的错误计数,以及"做了多少工作"的计数。冻结之后,一条可重复的命令输出那个指标,采样足够多以穿过噪声。

然后打开决策日志,一次尝试一行,记下假设、改动、前后值、差值、测试、判决(留下还是回退)。

循环是这样。把假设扎在架构模型里,让它命名一个具体机制(比如"把 X 从 boot 路径上推出去,因为它挡住了首次绘制"),而不是"试试加个缓存"。把改动交给一个 subagent,范围收紧。用冻结的 harness 前后测量,跑回归门。只有指标越过噪声、门保持全绿,才接受。否则把改动整个回退。一个接受的修复一个 commit。

它还有一条关于平台期的规矩:卡住的时候,连续几个拒绝之后,换类别、合并差一点成功的、重读源码,或者在断定山爬完之前先试一个更激进的想法。

## prototype

`prototype` 是一次性的草图,用来便宜地做一个设计或行为决定,或者用观察去解决一个经验分歧,而不是去问人。

它在 scratch 目录里建,把变体放在一个 switcher 后面,驱动每一个,截图或计时。顺序是它自己回答开放问题,而不是把问题交给你。

它也适用于行为和算法,不只是 UI。它是"用代码做计划":让 agent 通过跑点东西来回答自己的开放问题,并且留下空间给一个你本来想不出的选项。

关键在"一次性"。原型的价值在于它便宜、可丢弃。一旦它开始被认真维护,它就不再是原型了。

## visual-parity

`visual-parity` 做像素级的 UI 等价:匹配两个实现,或者迁移一个 styling 系统。

它对着一个冻结的 baseline 逐张 diff 截图,而不是用眼睛判断。眼睛会适应,截图不会。

迁移的时候有一条要主动声明:"bugs included"。别让迁移顺手修东西,否则新旧输出就没法比较了,你也就失去了等价这件事本身。

## 把七个连起来看

它们共享一条纪律:说清你观察到了什么,让 playbook 去要证据。每个 playbook 负责你没打出来的那一步。

有几对关系值得留意。`bug-fix` 和 `tdd` 是一对,当 bug 有廉价本地测试路径时,`tdd` 给 `bug-fix` 提供"先红后绿"的 commit 顺序。`perf-issue` 和 `hillclimb` 是一对,一个是一次性修复,一个是持续循环。`prototype` 和 `visual-parity` 是一对,一个用来探路,一个用来精确对齐。`refactoring` 和 `feature` 是一对,结构变行为不变,对比加行为。

边界也要说清。一个大的、跨切面的努力,即使某个更窄的 playbook(比如 feature)看起来合适,也路由去 `figure-it-out`,因为它需要的是为这个任务定制的、可审计的工作流,而不是一个通用模板。

## 今天就做一件事

下一次构建,先把两句话写清楚,再开始。一句是"我观察到了什么",一句是"done 怎么检查"。这两句就是路由信号,也是 playbook 愿意为你要证据的前提。
