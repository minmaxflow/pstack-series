# pstack 拆解 12 · 构建循环

你让 agent 加个功能。它写得很快,测试也过了,两周后你却发现它从一开始就抓错了数据形状。

构建的难点通常不在写代码,而在你对自己在做什么有多清醒:是复现一个已知缺陷,还是加一个新行为;是在重构还是在修 bug。姿态一错,后面的标准全错。所以每条 playbook 都逼你先把两件事说清楚:我观察到了什么,以及怎么算做完。

它们共享一条纪律:**说清你观察到了什么,然后让 playbook 去要证据。**

你不需要把这些步骤全写进 prompt。你说症状,说完成条件,playbook 会补上你没打出来的那几步:修之前先复现,实现之前先命名数据形状,重构之前先钉住行为,优化之前先 profile。

## feature

你拥有设计,委派实现。设计和实现是两种不同的工作:设计错了,越早发现越便宜;实现是体力活,可以安全地交出去。把它们分开,既能让设计错在写大量代码之前被抓住,也让两份工作各自有清晰的审查标准。

`feature` 做新行为或改过的行为,从一个命名好的数据形状建起。

它的步骤是固定顺序。

1. 先跑 `how`,摸清受影响的子系统。
2. 跑 `architect`,做并行设计探索。
3. 写 throughput checkpoint,把它铺成四个 todo:
   - **阻塞性第一步。** 哪些关卡必须在 fan-out 之前跑。
   - **独立工作流。** 哪些是互不相干的文件、服务或层,可以并行;共享写要串行。
   - **共享可变状态。** 默认拆开写目标;只有真实不变式才串行化。
   - **最小安全分解。** 如果一个 worker 最好,说明为什么。
4. 把写代码的任务委派给一个 subagent,用配置里的 feature 模型,给一个具体范围:文件路径、命名好的数据形状和它的组织方式、成功标准。当实现有多个合法形状时(错误处理、抽象层、测试结构),改用 `arena` 委派,让多个 runner 把备选摆出来,让 cross-judge 守住挑选。这一步是**强制的**,没有"跳过并说明"的出口。一个被禁止再派生 subagent 的 subagent,自己直接拥有这个 diff,但保持同样的审查分离。也不接受"我在等着内层 agent"这种回复。还有几条细节:注释按 Comments 的规矩,外科手术式地编辑,对从上游继承来的文件重新 grounding,把共享原语的改进移植到所有消费者并逐个验证。
5. 在**匹配的 surface** 上验证。`inconclusive` 或错的 surface 不算通过,要标出来。
6. rebase 成小而有顺序的 commit,后续栈起来。
7. 设计有争议的话,发布前先 `interrogate`。
8. 走 opening-a-pr。

它有一条关于 fan-out 的结构判断:**代码耦合的工作(一个功能、一次迁移)交给一个 owner,把 checkpoint 内联**,那个 owner 在阻塞阶段之后再内部 fan out。父层的 fan out 留给那些产出**独立产物**的切片:审计、跨子系统的调查、互相竞争的实验。

它的回复要点名:你建了什么、你选了什么以及为什么、throughput checkpoint、还开着的决定,设计备选用表格。

## refactoring

`refactoring` 是行为不变的结构改动。它有一句总纲:**你拥有契约,结构会变,行为不会。**

它和 feature 的区别是加行为,和 bug-fix 的区别是修行为。如果清理过程中暴露出一个缺失功能或一个真的 bug,拆出去,**先把这次结构改完、发出去**。一次重画是允许的,但要命名它、路由到 feature。大的、跨切面的结构工作,属于 `figure-it-out`。

它的步骤。

1. **先钉住行为契约。** 跑 `how` 学清楚现在的契约,然后写一个 characterization test、一个 snapshot,或者一个等价 harness,在任何结构移动之前把当前行为捕获下来。如果这块区域没有覆盖,**先写 pin 再碰结构**。它明确说:类型检查和 lint 不算 pin。
2. 命名代码缺失的那个结构。如果当前形状已经清楚、局部、不太会长大,无聊的代码留下。重塑造必须删掉分支或非法状态,不能只增加间接。
3. 命名目标形状:如果今天建,模块布局、类型、调用图应该是什么样。跨函数边界时先跑 `architect`。
4. 先减后加:删死代码、折叠单调用者包装、丢掉多余校验、清掉孤儿引用,再引入新形状。最小的、能到达目标形状的改动才发。一个"可能有用"的推测性清理,回退。
5. 小步移动,每一步保持 pin 绿。API 重塑的同一波里,迁移所有调用方、删掉旧 API,不要兼容垫片,不要新旧并存的路径。它还点了一个容易漏的地方:**重命名会静默地在字符串、prose、反向引用里漏掉用法**,所以每一次重命名都要对着真实文件抽查。
6. 在**真实产物**上证明行为没变,不是"能编译"。大一些的重塑跑一次等价检查:一个 diff 新旧输出的脚本,一个把录下来的基线在新代码上重放,或者一次在匹配 surface 上的冒烟运行。
7. 确认这次改动值得保留。成功的标准是 **reader load 降低了**。如果这次 diff 没有在某处降低 reader load,回退它。
8. rebase 成有序 commit:一个减法的 commit,然后重塑,然后后续清理。

## bug-fix

用科学方法修 bug。修 bug 最容易犯的错是凭直觉改一个"看起来像"的地方,然后因为现象偶尔不复现而以为好了。所以它要求每一行上线的代码都能追溯到运行时证据,"可能有用"的双保险不算,因为那是一个假设,不是修复。

`bug-fix` 的原则说得最直白:**你是这个任务的负责人。计划、审查、验证。**

它要求你用科学方法。每一行上线的代码都能追溯到运行时证据。"可能有用"的双保险,只是一个假设,它不发。证据推翻了假设,就把促使它的那个改动一起回退。**最小的、被证据支持的那个改动才上线。**

它的步骤。

1. **自己复现。** 在匹配的 surface 上,通过对应的 control skill,即使某个调试协议让你去请用户复现。只有在你能说出一个具体理由、说明 control surface 够不着目标,而且你已经驱动到它能到的极限之后,才去问用户。如果它不直接复现,就合成触发条件、收紧条件、或者插桩直到它触发。
2. **二分查找原因。** 形成候选假设,一个个排除,直到只剩一个。种子来自 `how`(受影响的子系统)和 `why`(回归史)。每一轮取那个能砍掉最多剩余问题空间的切分,拿运行时证据,排除掉。程序状态不清楚时就插桩,读代码运行时发生的实况。**不要猜。** 一个又长又顽固的排查用 `/loop` 驱动。在进入第 3 步之前,用运行时证据确认存活下来的**机制**。
3. 规划修复。跨函数边界先 `architect`。把实现委派给一个 subagent,用配置里的 bug-fix 模型,范围具体。
4. **在同一个 surface 上验证。** 原始 repro 现在通过。`inconclusive` 或者错的 surface 不算通过,要标出来。它还补了一句:**单元测试显示的是分支行为,不是 bug 消失。**
5. **让失败的 repro 先于修复进 git 历史。** 当 bug 有廉价本地测试路径时,用 `tdd` 的失败测试优先节奏;如果测试昂贵、集成重、或不清楚,跳过它。
6. 走 opening-a-pr。

它的回复要求:哪里坏了、根因、修复、你怎么验证的,并且**逐字粘贴"先失败、后通过"的 repro 输出**。

## perf-issue

性能是一门测量学科,不是读源码猜。"这段代码看起来慢"和"这段代码实测占了多少时间"常常是两回事,而优化一个并不是瓶颈的地方,非但没有收益,还白添了复杂度。所以每个修复都要绑到一个测量上。

`perf-issue` 追踪一个测量到的慢,对着基线改进。它的总纲是:**你拥有测量叙事。计划、审查、验证这些数字。把每一个修复绑到一个测量上,不要用读源码代替测量。**

它是一次性修复,这就是它和 `hillclimb` 的区别:那个是持续循环。

它的步骤。

1. 通过对应的 control skill 捕获一份基线 trace。用 `benchmark-checklist` 审基线,以及之后每一个数字。
2. 用 `how` 给假设做种子。**不要在没跑过的前提下声称一个性能天花板。** 它给了一串"性能咒语",按最便宜的优先试:

   1. 别做它。结果没人用的工作,停掉它,而不是把它变便宜。
   2. 做它,但别重复做。
   3. 少做它。
   4. 晚点做它。
   5. 趁他们没看的时候做它。
   6. 并发地做它。
   7. 更便宜地做它。

   靠前的咒语一旦达到目标,就停。

3. 从 trace 规划修复。跨函数边界先 `architect`。委派实现,用 perf-issue 模型。审查 diff。捕获修复后的 trace。每个尝试验证过再试下一个。
4. 解析并对比产物(JSON 进 sqlite 做 diff)。`inconclusive` 或错的 surface 不算通过。
5. 在 PR 里引用这次测量。
6. 走 opening-a-pr。

回复要点名:基线数字、修复后数字、差值、产物路径。

## hillclimb

`hillclimb` 是对一个可测量的东西持续、科学地改进,对着一个目标。它和 `perf-issue` 的区别,是它有一个循环,不只是一次修复。

它的核心纪律只有一句:**一个改动,一次测量,留或回退。** 永不堆叠未测的改动,永不从代码审查里宣称一个赢。

它的步骤。

1. **先 ground 工作负载和架构。** 跑 `how`,命名那些能移动结果的现实维度(数据大小、历史、状态、并发),选一个能复现用户抱怨的用例。**如果没有用例能复现它,先修 repro,不要开始爬山。** 然后定一个指标、一个"哪个方向算更好"、以及一个可检查的停止谓词。这个谓词要**把一个目标和一个尝试次数的下限配在一起**,比如"比基线好至少 50%,且至少 10 次迭代",好让一个早来的幸运胜利不能结束整轮。数字用用户给的,没给就跟他约定。
2. **建测量 harness,证明它的敏感度,然后冻结它。** 跑一些对比鲜明的现实工作负载,确认目标用例复现症状,而更容易的用例如预期地分开。如果 harness 分不开它们,改工作负载或指标。冻结之前用 `benchmark-checklist` 审它,让它打印错误计数和"做了多少工作"的计数。冻结之后,一条可重复的命令输出那个指标,采样足够多以穿过噪声(中位数,不是单次)。在任何改动之前,记下基线指标和回归门的一次绿跑。
3. **打开决策日志。** 用 `show-me-your-work`,一行一次尝试:id、假设、改动、前值、后值、差值、测试、判决(留或回退)、备注。每次尝试之前先读它。
4. **把假设扎进架构模型**,让它命名一个具体机制("把 X 从 boot 路径上推出去,因为它挡住首次绘制"),而不是"试试加个缓存"。性能类的假设按第 2 步的咒语排序。
5. **循环,一次一个假设。** 把改动交给 subagent(用 hillclimb 模型,范围收紧),监督并审查 diff,而不是自己敲。用冻结的 harness 前后测量,跑回归门。只有指标越过噪声、门保持全绿,才接受;否则把改动**整个**回退。一个接受的修复一个 commit,只 `git add <files>`,绝不 `-A`。无论留还是回退,都记一行日志。保留几个独立假设同时活时,并行发给不同 subagent,各在自己的 worktree。
6. **越过第一个平台期。** 卡住的时候(连续几个拒绝),换类别、合并差一点成功的、重读源码,或者在断定山爬完之前先试一个更激进的想法。正确性和简单性排在数字之上。一个赢了数字但破坏行为的改动回退;一个保持住数字的简化留下。
7. **在谓词满足时停,或者当剩下的想法都很边际、不值它的成本时停。** 不放松谓词去满足它,也不在还有便宜、没试过的假设时退出。真卡住了就浮出来,不要空转。
8. 走 opening-a-pr,把接受的 commit 按落地顺序堆起来。

回复要点名:指标和目标、基线到最终的百分比差值、迭代次数(留 vs 回退)、每个接受的修复一行、决策日志路径、以及如果再推进一步你会试的最好想法。

## prototype

`prototype` 是一次性的草图,用来便宜地做一个设计或行为决定,或者用观察去解决一个经验分歧,而不是去问人。

它的总纲里有一句很关键:**它是唯一一个 playbook,让 Laziness Protocol 的"最小改动"和验证的门槛同时反转。** 速度优先于打磨,代码质量无所谓,不做规划。这里的 rigor,在于**便宜地选对设计**。它鼓励你提出用户没要求的变体,扔掉一个方向再试另一个。

它的步骤。

1. **界定这个原型存在的目的**:要做的决定是哪个布局、哪个交互、哪个密度,还是对一个经验分歧,哪种行为、哪种时序、哪种做法。**没有决定就没有原型**,路由到 feature。
2. 设计空间开放时,先收集参考:找找有没有先例,总结一版主题、配色、布局的 moodboard,让用户在动手之前先挑方向。方向已定就跳过。
3. **在隔离的 scratch 目录里建一次性版本**,和产品源码分开。视觉决定用原生 HTML/CSS/JS,或者能渲染出这个想法的最轻的栈,用 CDN 依赖,一个带热重载的 dev server。行为或时序决定用能验证那个问题的最小脚本。不用生产框架,不写测试,不做抽象。
4. **对比备选时,把它们放在一个 switcher 后面**(按钮或按键),每个变体有标签。这是 exhaust-the-design-space 的廉价实现。
5. **在匹配的 surface 上验证。** 视觉决定:通过 control skill 给每个变体截图,并驱动那个交互。行为或时序决定:通过记录时序、打印输出、或者观察渲染,来观察你正在决定的那件事。**在这里,观察就是测试,不是一个断言。**
6. 呈现备选、权衡和一个推荐。输出是**决定加那个一次性产物,不是可发布的代码**。把选定的方向交给 feature(或形状问题交给 `architect`)去做真正的构建。

回复要点明:探索了哪些变体、证据(视觉决定给截图,行为决定给观察到的输出或时序)、权衡、你的推荐、scratch 路径,并且**明说这个原型是一次性的**。

## visual-parity

等价不是一个感觉,是一个可以量化的差。眼睛会适应、会疲劳、会被期望欺骗,所以它不能当裁判;截图对比可以。这也是为什么 baseline 本身就是规范:先冻结一份当前行为的截图,之后每个改动都对它做 diff,非零就是失败。

`visual-parity` 做像素级的 UI 等价:匹配两个实现,或者迁移一个 styling 系统。它的总纲是:**你拥有像素级等价。baseline 就是规范。你不碰它。**

它的步骤。

1. **在任何迁移之前,先建立 baseline**:一个视觉回归 harness,给当前组件在它的各种状态下截图;匹配两个实现时,也给目标截图。**没有 baseline,就没有等价声明。** 这是一个阻塞性前置,不是后续工作。
2. **声明并守住反捷径条款**:不修改 harness,不动 baseline,不为了 diff 通过而重构组件。如果 baseline 看起来是错的,**停下来问,不要编辑它**。
3. **一次迁移一个组件。** 跨 worktree 并行,一个组件一个 owner。共享原语作为阻塞阶段**先迁移**。
4. 通过 control skill,在匹配的 surface 上,用图像 diff 验证每个组件对它的 baseline。**非零 diff 就是失败。** 调查那个像素差。用 `/loop` 按组件驱动,直到 diff 为零。
5. 走 opening-a-pr,按组件或按安全的批次。

迁移的时候有一条要主动声明:**"bugs included"**。别让迁移顺手修东西,否则新旧输出就没法比较了,等价这件事本身就失去了意义。

## 把七个连起来看

它们共享一条纪律:说清你观察到了什么,让 playbook 去要证据。每个 playbook 负责你没打出来的那一步。

有几对关系值得留意。`bug-fix` 和 `tdd` 是一对,当 bug 有廉价本地测试路径时,`tdd` 给 `bug-fix` 提供"先红后绿"的 commit 顺序。`perf-issue` 和 `hillclimb` 是一对,一个是一次性修复,一个是持续循环。`prototype` 和 `visual-parity` 是一对,一个用来探路,一个用来精确对齐。`refactoring` 和 `feature` 是一对,结构变行为不变,对比加行为。

`prototype` 是这一组里唯一一个把常规纪律反过来用的:它让 laziness 和验证门槛同时让位,因为它的目的不是交付,是**用一个便宜的东西把一个决定做对**。这也解释了为什么它明确说"输出不是可发布的代码"。

边界也要说清。一个大的、跨切面的努力,即使某个更窄的 playbook(比如 feature)看起来合适,也路由去 `figure-it-out`,因为它需要的是为这个任务定制的、可审计的工作流,而不是一个通用模板。

## 今天就做一件事

下一次构建,先把两句话写清楚,再开始。一句是"我观察到了什么",一句是"done 怎么检查"。这两句就是路由信号,也是 playbook 愿意为你要证据的前提。
