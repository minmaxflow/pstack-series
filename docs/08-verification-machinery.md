# 08 · 验证机械

第 04 篇讲的是"什么算证明"。这一组四个 skill 是把那句话变成可以跑的工具。

你问 agent 验证过了吗,它说验证过了。你再问怎么验证的,它说跑了一遍测试。问题就在这句话里。跑测试,和证明应用行为,不是一回事。

## tdd

把破坏变成可执行的。在动生产代码之前,先让那个坏行为能在一条命令里重现:修复于是有了一个能过或不过的判据,而不是一句"应该好了";git 历史里也因此留下一条"先红后绿"的论证,别人不用信你,跑一遍就知道。这条原则也有它的代价意识:不是所有 bug 都值得造测试,当测试路径昂贵或脆弱时,用最接近的可执行检查代替,仍然好过一篇无法验证的说明。

`tdd` 讲的是当 bug 有一条廉价的本地测试路径时,先写最小的、因为正确原因失败的测试,再修,再重跑。

它有一条很明确的适用边界,而且两边都写清楚了。**用它**,当用户明确要 TDD、要一个失败测试、要一个回归测试,或者这个 bug 明显有一条廉价的本地测试路径。**跳过它**,当测试路径不清楚、昂贵、集成很重,或者用户根本没要。

它甚至进一步说明:一个测试如果会需要大范围搭 harness、脆弱的 mock、慢的端到端基础设施、只在生产才有的状态、含糊的复现步骤,或者会导致大量无关的 fixture 改动,那就别为它硬造测试,改用最接近的可执行检查。它有一句判据很干脆:**宁可不要新测试,也不要一个坏测试。**

那什么叫坏测试,它给了定义:一个主要在测 mock 的测试;一个把当前实现细节写死的测试;一个依赖时序或无关全局状态的测试;一个为一个小修复却需要昂贵基础设施的测试;一个证明完这次修复就会被立刻删掉的测试。

满足条件时,它的流程是六步。

1. **理解 bug。** 弄清预期行为、当前行为、受影响的路径,以及最小的可观察复现。
2. **选最窄的可执行检查。** 优先用这条代码路径已经在用的、最接近的单元、组件、集成或回归测试。如果没有明显可行的测试路径,不要为了走流程而从零造一个。
3. **先写失败测试。** 加最小的、能抓住这个 bug 的那个测试。它要**编码预期行为,不是复刻当前实现**。
4. **修之前先跑它。** 确认它是因为**正确的**原因失败。如果它通过了,或者因为一个无关原因失败,先纠正测试或复现,再动实现。
5. **修 bug。** 做最小的、能满足预期行为、同时保住周围契约的实现改动。
6. **重跑回归测试。** 确认它现在通过。

它的护栏也值得记:不要为了迁就一个错误的实现去改测试;不要削弱已有的断言,除非预期行为真的变了而且理由清楚;回归测试聚焦在这个 bug 上,避免大范围 fixture 改动;如果是 flaky 的 bug,尽量让测试确定化,并写下被锁住的信号;如果这个 bug 暴露出更大的一类问题,先把聚焦的回归路径落地,再考虑加兄弟覆盖。

最后一条回复纪律也很有意思:**报告证据,不是报告结果。** 它要求点名"修之前失败的那个测试或可执行检查"以及它产生的失败,点名"修之后通过的那次运行"以及周边的验证,如果无法演示失败在前,就说明为什么,并描述替代的最接近的回归检查。

## benchmark-checklist

一个数字是一个关于系统的声明,而声明可以是真的,也可以只是看起来是真的:一次坏掉的运行照样会打印一个合理的数字。所以它把"这个数字到底测了什么"变成七个必须用运行证据回答的问题,而且明确了什么时候"没有可测量的区别"或"不确定"才是唯一诚实的结论。

`benchmark-checklist` 把 explain-the-number 变成了七个问题,每个问题都要一个来自真实运行的答案,不是从代码里猜的答案。

动手之前先做三件事。把你打算写进结论的那句话写下来,七个问题是用来检验这句话的。读一遍测量脚本,弄清它计的是什么、忽略的是什么。看一眼机器的负载和核数,如果机器正忙,找出在跑什么,停不掉就让两侧交替跑,让它们看见同样的噪声。

然后是那七个问题。

1. **为什么不是翻倍?** 说出那个限制。profiler 会拖慢被测量的东西,所以另做一次不加 profiler 的跑来取限制:用 `top`、`pidstat` 看每个进程的 CPU,用 `node --cpu-prof`、`py-spy`、`perf` 看运行时热点,看 I/O 等待,看 syscall 数。然后把热点映射回源码。也要盯着 load generator,如果它先饱和,你测的是它。如果一个改动没有让数字动,限制能解释为什么,所以在断定这个改动没用之前,先找到限制。
2. **调优了吗?** 每一侧都按生产的方式跑:release 构建、生产的 flag 和环境、批处理和事务设置、连接池、和生产一样冷热程度的缓存、相同的版本和数据。如果有一侧还在默认设置上,你比的是配置,不是实现。如果那个限制本身就是一个设置(每行一次提交、一个 debug 构建、少一个索引),那一侧就是没调优,调好再测,测不了就不要从这个运行里选赢家。
3. **突破极限了吗?** 做算术。把每秒字节数对硬盘和网络带宽,把每秒操作数乘单次成本对核数。再看时间账:去掉一个只占 10% 的环节,整个流程最多快约 11%。一个越过极限的结果,说明这次运行测的是别的东西,比如缓存、空操作,或者一个 bug。
4. **报错了吗?** 数失败和异常响应,确认输出是对的,不是"存在"。失败和成功的行为不一样:被拒绝的请求往往很快,超时和重试很慢。如果脚本没数错误,把计数加上。
5. **复现吗?** 每一侧至少跑五次,并且交替跑(A、B、A、B),让预热、懒初始化、缓存和漂移不会偏向某一侧。报告中位数和范围。比噪声还小的差距,算没有可测量的区别。差距很接近时,用秩和检验或 harness 自带的统计。
6. **重要吗?** 在任何微观结果旁边,测一次用户真正要等的端到端路径,用真实的数据量和并发。把微观结果报成整体的一部分。一个只占一次请求 1% 的 helper,最快的优化也只能让请求快 1%。
7. **真的发生了吗?** 确认工作发生在计时区间里。请求到了服务器,行被写进去了,字节被读了,代码用了那个结果。没有被迭代的生成器、没有被 await 的 promise、被 JIT 丢掉的结果、超时,都会为一件根本没发生的工作打印一个数字。

有一个例外。用户只要一个粗略的感觉时,跑一次就够,但仍然要检查第 4 和第 7 条,并且说明这是单次运行。而在两个选项之间做选择,永远不是"粗略的感觉",必须走完整套。

它的结论是四种之一:更快、更慢、没有可测量的区别、不确定。每种都带上 run count、范围、限制。三种情况会给"不确定":你声称有差别却说不清限制,有一侧没调优,或者第 4、7 条没法检查。

它还把报告的形状定死了:先给判决,再给数字、run count、范围和限制。一个 PR 的描述里只放一个主数字,其余运行细节放进一个链接的产物或笔记文件。

谁在用它。poteto-mode 在 perf-issue 和 hillclimb 两个 playbook 里已经自动跑了它:前者在据此规划之前先审基线,以及之后每一个数字;后者在冻结 harness 之前先审它。

## create-verification-skill

验证是承重柱,而它最慢的一步是在等一个人:agent 改完,把结果交回给你手工检查。让 agent 能自己驱动真实应用、自己留下证据,就是把"等人"从关键路径上拿掉。一次投入,之后每一次运行都受益,所以它是 setup 里回报最高的一件事。

`create-verification-skill` 生成一个项目本地的 skill,教 agent 像用户那样驱动你的应用,并留下证据。

如果 setup 里只做一件事,做这一件。原因是它改变的不是一件事,是所有事的上限。guide 里点得很清楚:一个能自证的 agent,会一直跑到检查通过;一个不能自证的 agent,把每一个结果都交回给你手工检查。你花一次力气换来的,是之后每一次运行都不再需要你来当验证的瓶颈。

它跑起来是去 **interview 仓库,不是 interview 你**。它自己回答五个问题。

- **Surface**:用户到底碰什么?web UI、CLI/TUI、桌面应用、API、移动端,还是一个库?一个仓库可能有好几个,选主要的,其余的记下来。
- **Run**:本地怎么启动?优先用仓库自己记录的命令(package scripts、Makefile、README 的快速开始),记下端口、环境变量、种子数据、鉴权。
- **Drive**:agent 怎么程序化地交互?已有的 harness 优先:Playwright 或 Cypress 的用例、expect 脚本、PTY 助手、可以 curl 的端点、一个调试端口。实在没有,才选通用方案:web 和 Electron 用浏览器加 CDP,CLI/TUI 用 tmux 或 PTY,服务用纯 HTTP。
- **Observe**:能抓到什么证据?截图、终端记录、响应体、日志、退出码、数据库状态。
- **Isolate**:能不能并排跑两个实例(端口、数据目录、profile)?不能的话,要在生成的 skill 里写清楚:拒绝同时驱动一个共享实例,比弄坏用户的会话好。

它只问你代码答不上来的部分。而且有一个前置条件:**如果这个 checkout 现在根本构建不起来或者启动不了,先修那个,再生成。** 一个建立在坏地基上的验证 skill,会教出一串错误的步骤。

输出是 `<skills>/verify-<app>/`,一份面向 agent 的指令,包含精确的五节。

- **Launch**:启动应用进行验证的确切命令,以及怎么判断它准备好了(一行日志、一个端口回应、一个提示符),还有拆解方式。短命的 CLI 或 TUI 没有要一直活着的服务器,启动就是"构建一次二进制",然后每次驱动开一个自己的 PTY 或 tmux 会话。
- **Doctor**:一个只读的检查,回答"这个实例值不值得驱动":进程活着、版本或构建对、端口是自己的、鉴权有效。agent 在遇到任何不对劲时,第一件事就是跑它。
- **Drive**:带着这个仓库真实选择器和命令的 harness 配方,不用示例。优先稳定的句柄(ARIA 标签、data 属性、提示符字符串、路由路径),不用坐标和 tab 顺序。
- **Evidence**:一次证明要抓什么,放到哪里。它规定了证明的标准:走真实的用户路径,不走内部 setter 或测试专用端点;抓动作**和**它导致的状态,不只抓最后一屏;在可见结果之外验证副作用(写进去的文件、插入的行、发出的消息);只在生产边界已经隔离了外部系统的地方用 mock。还有一个很实在的提醒:当安全路径是一个 dry-run 或测试模式时,要靠观察(文件、网络、git ref)确认它到底跳过了什么,不要信它的名字,因为有些 dry-run 还是会碰网络或打开浏览器。
- **Cleanup**:怎么拆掉这次运行创建的实例。绝不按进程名杀,只杀自己启动的。清理移除实例和临时状态,绝不移除证据:证明产物要在拆解之后活下来,放在 skill 指定的位置。

再加一个 `features/` 目录下的 feature map,每个功能一个文件,从用户视角回答:这是什么、怎么到达、怎么驱动、什么可观察的终态能证明它工作。起步先做最上面的三到五个,从路由、命令、菜单或文档里找。四个固定的二级标题是 Sub-features、How to get to it (user POV)、Driving it with \<harness\>、Gotchas。

它有一条纪律不能省。**生成器在交给你之前,自己把这个 skill 端到端证明一遍**:启动,跑 doctor,驱动一个功能(一个就够,feature map 的意义就是让以后的运行覆盖其余),抓证据,清理。而且清理之后要确认证据**还在原处**,一个会吃掉证据的 cleanup 这一关就算失败。这一步没过的输出,不要用,它是一个草稿,不是一个交付物。

从此刻起,"在应用里验证它"变成这个仓库里任何 agent 都能执行的一步,不需要一次设置对话。这个 skill 应该提交进仓库,当成基础设施。

## maintain-verification-skill

基础设施会腐烂,这是默认状态,维护才是需要投入的动作。feature map 和别的基础设施一样,不会自己保持诚实;应用改了而 map 没改,验证就开始说谎。所以它把"保真"也变成一个例行工作:有固定流程,有明确的三种结局,而且绝不拿文档去盖住一个真实的产品回归。

应用会变,feature map 会腐烂。`maintain-verification-skill` 就是来保真的。

它的单位是**功能,不是每一句话**。目标是每个功能都从源码覆盖到、都真机跑一遍,而不是把每条 bullet 都推翻重写。

它只有三种结局,而且要明说选了哪一种。

- **clean**:每个功能都拿到了源码和实机覆盖;没有值得发的东西。不建分支,不开 PR。
- **changed**:一个 PR,发已证明的文档、harness 或 map 修正。
- **blocked**:覆盖没跑完,或者一个已证明的修复没法安全发出去。说清楚到底是什么卡住了。

它有一条必须守住的编辑边界:**只改验证 skill 自己的目录**(它的 `SKILL.md`、`features/`,以及它自己的 harness 脚本)。**运行期间绝不改产品代码。** map 描述的一个行为,应用已经不做了,那要么是文档漂移(修 map),要么是产品回归(报告它,不要在文档里盖过去)。

一轮 pass 分六步。

**第 0 步:找到目标。** 找到要维护的那个验证 skill:项目本地、正文里有启动和驱动小节、且有 feature map 的那个,通常在项目 skill 目录里的 `verify-*/`。有多个候选就问你要哪个;一个都没有就停下来,指向 `create-verification-skill`,不要自己发明一个目标。

**第 1 步:索引卫生。** 读 feature map 的 README,glob 它同级的文件。修掉缺失的、多余的、重复的、死的条目。轻量,不生成完整清单。

**第 2 步:源码波。** 一个只读 subagent 管一个 feature 文件,并发起。每个从源码解释"这个面向用户的功能是怎么工作的",标出可能的文档漂移并给出引用,返回一份简洁的实机验证配方。子 agent **绝不驱动应用,绝不改文件**。返回形状是:功能摘要、源码入口、可能的漂移或无、一份配方。

**第 3 步:对齐。** 每个 feature 文件都要有一份返回的摘要。把重叠的配方合并成尽量少的应用状态。抽查被引用的漂移,干净的说法不要重新证明。扫一遍最近的改动,看有没有面向用户的界面漏在 map 之外,但把它标成"缺失"之前必须有一个具体源码路径。

**第 4 步:实机波。** 即使源码看起来干净,这一步也是必需的。**协调者拥有全部驱动权**,按验证 skill 自己的启动模型来:服务器和 UI 用一个长期实例串行驱动,短命 CLI 每次开一个新的隔离会话(由 skill 的 Launch 一节决定,不是这一步决定)。

整轮 pass 要守住三条不变式,不管遇到什么失败。

1. **绝不驱动一个自上次出意外以来没做过健康检查的实例。** 第一次驱动前 doctor,每个新会话开始时 doctor,任何失败驱动之后 doctor。doctor 看不到的失败(健康进程上卡住的 UI 状态),就重置到一个已知状态或者重启,不要指望它自己好。
2. **已经抓到的证据要在每一次清理之后活下来**,要在它指定的位置检查,不能假设。
3. **一次驱动启动的任何东西,都不能活过那次驱动的有效期。** 失败迭代留下的残留要清掉,不管会话是卡住的、退出的,还是共享的(共享实例就清残留,不清实例)。

由 skill 漂移导致的 doctor 失败也是漂移:在编辑范围内修掉,重试一次,只重启这个修复让它失效的东西,然后再判定 `blocked`。一个到不了的功能,只有带上具体前置条件(鉴权、权限、操作系统、外部状态)和尝试过的路由,才能标成 `verified-unreachable`;如果 map 漏了那个前置条件,那就是漂移。任何来自分诊的 harness 修复,都要在上线前重新实机驱动一遍。最后一次驱动之后再做最终拆解,确保没有东西活过这次运行。

**第 5 步:分诊。** 用户视角的描述错了或漏了,是文档漂移,修掉。能工作的行为但 harness 驱动不了,是 harness 缺口,修掉。应用行为真的坏了,是产品缺口,记录给你,留在这个 PR 之外。

**第 6 步:发或停。** `changed` 就发一个已证明修正的 PR,发之前把每个改过的文件重读一遍。`clean` 或 `blocked` 就说明结局和覆盖情况,不开 PR。

它建议的节奏是至少一天一次,最好来自一个定时的自动化,这样没有人需要记得它。验证基础设施和别的基础设施一样,腐烂是默认状态,维护才是需要投入的动作。

## 把四个连起来看

这一组是第 04 篇的机械。

`tdd` 把"先红后绿"变成 commit 顺序,还给了它一条诚实的退出通道:测试不划算时,用最接近的可执行检查,并说明为什么。`benchmark-checklist` 把"解释这个数字"变成七个问题,还规定了"不确定"什么时候是唯一诚实的结论。两个 verification-skill 把"对着真实产物检查"变成项目里任何 agent 都能跑的基础设施。

两个 verification-skill 是一对。`create-` 负责生成,`maintain-` 负责保真。一建一守。它们的编辑边界也互相呼应:`create-` 生成时只写自己那份 skill 的目录,`maintain-` 维护时也只改那个目录,产品回归一律报告,不掩盖。

边界也要说清。不要在一条真实命令是更强证据的地方硬塞测试。verification skill 是基础设施,要提交进仓库,让每个人和每个 agent 用同一种方式驱动应用。当一个团队反复让 agent 写一次性脚本去点应用,正确的回应是请它写一个小的控制 CLI,让 skill 去调,agent 少花 token,每次运行都可复现。
