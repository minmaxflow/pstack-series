# 08 · 验证机械

第 04 篇讲的是"什么算证明"。这一组四个 skill 是把那句话变成可以跑的工具。

你问 agent 验证过了吗,它说验证过了。你再问怎么验证的,它说跑了一遍测试。问题就在这句话里。跑测试,和证明应用行为,不是一回事。

## tdd

`tdd` 讲的是当 bug 有一条廉价的本地测试路径时,先写最小的、因为正确原因失败的测试,再修,再重跑。

它其实是 sequence-verifiable-units 的最典型形状。失败测试在前,修复在后,这个顺序在 git 历史里留下一段"先红、后绿"的论证。别人不用信你的话,他们看这串提交就够了。

它有一条重要的自我克制。如果要做这个测试需要大范围搭 harness,或者需要一堆脆弱 mock,`tdd` 会自己说出来,然后改用最接近的可执行检查。不要在一条真实命令是更强证据的地方,硬塞一个测试进去。测一个真实约束,比测一个假装的约束有价值。

## benchmark-checklist

`benchmark-checklist` 把 explain-the-number 变成了七个问题,每个问题都要一个来自真实运行的答案。

1. 什么限制了这个数,为什么它不是翻倍。
2. 每一侧是不是都按生产的方式调优了。
3. 结果有没有突破物理极限,比如磁盘带宽或核数。
4. 有没有东西报错,或者返回了错的输出。
5. 交替多跑几轮之后,它还能复现吗,中位数和范围是多少。
6. 它在端到端上重要吗,在用户真正要等的路径上吗。
7. 工作真的发生在计时区间里吗。

它的结论是四种之一:更快、更慢、没有可测量的区别、不确定。每种都带上 run count、range 和 limiter。如果它说不出 limiter,或者有一侧没调优,它就给"不确定",不给一个好看的数字。

谁在用它。poteto-mode 在 perf-issue 和 hillclimb 两个 playbook 里已经自动跑了它。你自己在外面测了一个数,或者别人的数字好看得可疑时,自己敲它。

它是两条原则的合成:explain-the-number 给了它要问什么,build-the-lever 给了它"用脚本重跑"这个形态。

## create-verification-skill

`create-verification-skill` 生成一个项目本地的 skill,教 agent 像用户那样驱动你的应用,并留下证据。

如果 setup 里只做一件事,做这一件。原因是它改变的不是一件事,是所有事的上限。guide 里点得很清楚:一个能自证的 agent,会一直跑到检查通过;一个不能自证的 agent,把每一个结果都交回给你手工检查。你花一次力气换来的,是之后每一次运行都不再需要你来当验证的瓶颈。

它跑起来是去 interview 仓库,不是 interview 你。它自己回答五个问题:surface(用户到底碰什么,是 web UI 还是 CLI 还是 API),run(本地怎么启动,端口、环境变量、种子数据、鉴权),drive(agent 怎么程序化地交互,已有的 harness 优先,然后才是浏览器和 CDP、PTY、纯 HTTP),observe(能抓到什么证据),isolate(能不能并排跑两个实例)。只问你代码答不上来的部分。

输出是 `.cursor/skills/verify-<app>/`,一份面向 agent 的指令,包含精确的五节:Launch、Doctor、Drive、Evidence、Cleanup。再加一个 features/ 目录下的 feature map,每个功能一个文件,从用户视角回答:这是什么、怎么到达、怎么驱动、什么可观察的终态能证明它工作。

它有一条纪律不能省。生成器在交给你之前,自己把这个 skill 端到端证明一遍:启动,跑 doctor,驱动一个功能,抓证据,清理。而且清理之后要确认证据还在原处,一个会吃掉证据的 cleanup 这一关就算失败。这一步没过的输出,不要用。

从此刻起,"在应用里验证它"变成这个仓库里任何 agent 都能执行的一步,不需要一次设置对话。

## maintain-verification-skill

应用会变,feature map 会腐烂。`maintain-verification-skill` 就是来保真的。

它跑一遍审计:每个功能一个只读的源码阅读器,并行跑;然后一次 live pass,真正驱动所有被映射的功能。它只有三种结局。

`clean`,全覆盖,没有东西要发。`changed`,一个已证明修正的 PR,而且这个 PR 被限制在验证 skill 自己的目录里。`blocked`,点出那个阻塞。

最关键的一条:**它绝不编辑产品代码。** 如果 live pass 抓到了一个产品回归,它报告这个回归,不在文档里把它盖过去。一个会自我美化的验证工具,比没有验证工具更危险。

建议的节奏是至少一天一次,最好来自一个定时的自动化,这样没有人需要记得它。验证基础设施和别的基础设施一样,腐烂是默认状态,维护才是需要投入的动作。

## 把四个连起来看

这一组是第 04 篇的机械。

`tdd` 把"先红后绿"变成 commit 顺序。`benchmark-checklist` 把"解释这个数字"变成七个问题。两个 verification-skill 把"对着真实产物检查"变成项目里任何 agent 都能跑的基础设施。

两个 verification-skill 是一对。`create-` 负责生成,`maintain-` 负责保真。一建一守。

边界也要说清。不要在一条真实命令是更强证据的地方硬塞测试。verification skill 是基础设施,要提交进仓库,让每个人和每个 agent 用同一种方式驱动应用。当一个团队反复让 agent 写一次性脚本去点应用,正确的回应是请它写一个小的控制 CLI,让 skill 去调,agent 少花 token,每次运行都可复现。

## 今天就做的一件事

如果你的项目还没有一个能在应用里自证的项目本地 skill,先建一个。这是 setup 里回报最高的一笔投入,没有之一。
