# 09 · 交付与文体

代码写完不等于可以交付。这一组四个 skill 管的是产物读起来像不像人做的。它们照看三类东西:代码里的注释、散文、文档。

它们有一个共同的立场:**作者会替自己辩护,所以清洗要由一个没写它的人来做。** 这就是为什么这一组里既有清洗工具,也有一个独立的 reviewer。

## unslop

`unslop` 去掉书写里的 AI 痕迹。

它不是洁癖。那些痕迹让人读起来更费劲,而且往往是想得不够清楚的外在表现。举一个最直接的:写"运行得很快",是在躲开那个数字。规则要求你把数字说出来。

它维护一份模式清单,规则编号是稳定的,因为别的 skill 会按编号引用它。几个典型:

- 表面化的 `-ing` 短语("highlighting"、"ensuring"、"showcasing")。
- 模糊的归属("专家认为"、"有报道指出")。
- AI 词汇,比如 additional、crucial、delve、enhance、pivotal、showcase、underscore。
- 把"是"说得很花哨("serves as"、"stands as"、"boasts")。
- "不只是 X,而是 Y"。
- 硬凑三件套。
- 同义词轮换(一段里主角、主人公、核心人物、英雄轮流出现)。
- 假范围("从 X 到 Y",而 X 和 Y 不在同一个有意义的尺度上)。
- 破折号滥用。规则要求完全避开破折号。
- 冒号滥用。冒号用在列表或例子之前可以,当句中的连接词不行。
- 过度加粗,以及那种"加粗标签加冒号、结果只是把句子重说一遍"的 inline-header 列表。
- 标题用 Title Case。
- 聊天机器人短语和谄媚语气。
- 填充词、过度对冲、通用结论。
- 抽象隐喻名词(substrate、wedge、vector、flywheel 这一路)。
- 说感受不说机制("数据库触手可及"),而不是说机制或数字。

最后一条其实是整条 skill 的核心。问一个句子告诉了读者什么可以做的事、可以知道的事,然后把那个写出来。如果改成具体指令、事实或数字之后什么都没剩,就删掉它。

## technical-writing

`technical-writing` 是一套分层的文档标准,用在 docs、RFC、readme、PR 描述、commit message 上。

它的目标只有一句:一个疲惫的工程师在第一遍就能看懂。

做法是先选模式,再写句子。模式来自 Diátaxis,四个:教程、how-to、参考、解释。一篇文档先确定它属于哪一种,不要让一个教程漂移成参考和解释的混合体。

确定模式之后,一句一句地过:谁做什么,一句一个意思,没有一句话能被读出两种意思。它同时叠了 Google 的开发者风格、简化技术英语,以及全球英语的写法,目标都是同一件事:可读。

名字该点的时候就点。一个教程要保持是教程,别不知不觉变成参考。

## no-comments

`no-comments` 把注释交给一个**没写它的** reviewer,再处理被接受的发现。

为什么注释要单独走一遍,而且不能交给写它的那个 agent。原因很朴素:一个作者会像维护自己的东西一样维护自己的注释,你替我辩护,我也替你辩护。所以要换一双眼睛。

这个 reviewer 叫 Comment Sicko,只读,手上有一份很短的 keep 清单:license 头,公共 API 上的 doc comment,解释代码说不清楚的 why 的链接,以及由你无法改的外部依赖强制出来的行为。除此之外都走。你自己代码里蹦出来的意外,没有这种豁免。那条注释会作为一次重构信号回来。

它有一个很好的收尾动作。当一个注释声称一个约束,写着"不要删""不要改这段文案""改之前先问 X",`no-comments` 会提供一个把这个约束编码成类型、测试或 lint 的方案。要么编码它,要么删掉它。这其实是 encode-lessons-in-structure 在注释上的应用。

分工值得记清楚。`deslop` 清代码里的 slop,`unslop` 清散文里的 slop,`no-comments` 把注释交给一个没写它的人。

## typescript-best-practices

`typescript-best-practices` 把 type-system-discipline 落成具体的语法规则:用可辨识联合、边界上用 `unknown`、穷尽变体、从 schema 派生类型。

它为什么单独存在。因为那条原则是语言无关的,它讲的是"类型检查器是一个证明助手"。而这个 skill 负责把它翻译成 TypeScript 里可执行的写法。原则给你方向,这个 skill 给你语法。

有一个使用细节:它不会自己加载。当任务碰到 `.ts` 或 `.tsx` 文件时,要显式敲一下 `/typescript-best-practices`,它才会进入上下文。

## 把四个连起来看

这一组都在往外看,看的是"别人读你的产物"这件事。

`unslop` 管散文,`technical-writing` 管正式文档,`no-comments` 管注释,`typescript-best-practices` 把一条架构原则落进具体语言。它们的共同假设是:作者看不见自己的问题,所以需要规则清单,或者一个外部 reviewer。

边界也要说清。清洗不是可选的润色。一个带着叙述性注释和防御性死重的 diff,在 reviewer 眼里就是未完成,而且多出来的那部分代码,正是下一个 bug 藏身的地方。如果你自己都觉得这个 diff 有点撑,提交之前就清,别等 review 指出来。

## 今天就做的一件事

提交之前,分三样东西清。代码走 `deslop`,散文走 `unslop`,注释交给一个没写它的 reviewer。三件事指向同一个结论:让不在这段代码里投入过感情的人来看一遍。
