# 09 · 交付与文体

代码写完不等于可以交付。这一组四个 skill 管的是产物读起来像不像人做的。它们照看四类东西:散文、文档、注释,以及具体语言里的写法规则。

它们有一个共同的立场:**作者会替自己辩护,所以清洗要由一个没写它的人来做。** 这就是为什么这一组里既有清洗工具,也有一个独立的 reviewer。

## unslop

`unslop` 去掉书写里的 AI 痕迹。

它不是洁癖。那些痕迹让人读起来更费劲,而且往往是想得不够清楚的外在表现。举一个最直接的:写"运行得很快",是在躲开那个数字。

它的流程只有两步:扫,然后改写,改写时保住原意、匹配原本的语调。

规则用**稳定的编号**,因为别的 skill 会按编号引用它。一条规则被删掉,编号会留一个空位,不会重排。下面按类别过一遍。

**内容。**

- 表面化的 `-ing` 短语:"highlighting"、"ensuring"、"showcasing"、"fostering"。要么删,要么换成真正的来源。
- 模糊的归属:"专家认为""有报道指出""一些批评者主张"。要么点名,要么删。

**语言。**

- AI 词汇:additional、crucial、delve、enduring、enhance、fostering、garner、interplay、intricate、landscape(抽象义)、pivotal、showcase、tapestry、testament、underscore、vibrant。换成普通的词。
- 把"是"说得很花哨:"serves as"、"stands as"、"boasts"、"features"。直接说 is 或 has。
- "不只是 X,而是 Y"。直接说那个点。
- 硬凑三件套。用自然的数目。
- 同义词轮换:一段里主角、主人公、核心人物、英雄轮流出现。挑一个,重复它。
- 假范围:"从 X 到 Y",而 X 和 Y 不在同一个有意义的尺度上。直接列。

**文体。**

- 破折号滥用。规则要求**完全避开破折号**,用句号或逗号,连括号、短破折号、拿连字符当破折号都不要。
- 冒号滥用。冒号用在列表或例子之前可以,当句中的连接词不行。
- 过度加粗。不要给每个专有名词和缩写都加粗。
- 那种"加粗标签加冒号,结果只是把句子重说一遍"的 inline-header 列表。但一个以句号结尾、点名了条目、后面跟着**真正新信息**的加粗引导语("**Schema in TypeScript。** 表都放在一个文件里。")是可以的,不算这个毛病。
- 标题用 Title Case。用句子大小写。
- 装饰性 emoji。从标题和 bullet 里拿掉。
- 弯引号。换成直引号。

**交流痕迹。**

- 聊天机器人短语:"希望这对你有帮助!""有问题告诉我。""当然!""找到了!"
- 谄媚语气:"好问题!""你说得完全对!"直接回应。

**填充。**

- 填充短语。"为了"就是 to。"由于……这一事实"就是 because。"值得注意的是"删掉。
- 过度对冲。"也许可能或许可以论证它大概……"改成"可能"。
- 通用结论。"未来一片光明。"说具体的计划或事实。

**术语。**

- 抽象隐喻名词:substrate、wedge、vector、locus、vantage、nexus、primitive(名词)、harness(隐喻)、surface(指 API surface)、bedrock、scaffolding(隐喻)、modality、paradigm、gold-plating、ratchet(隐喻)、evacuate(指搬代码)、endgame、north star、flywheel。这些读起来很技术,但通常有一个更普通、更具体的词。substrate 换成 base,wedge in 换成 add,vector 换成 way。

**口语。**

这组是整个 skill 的核心,值得单独说。

- **说它做什么,不说它感觉像什么。**"数据库触手可及""能读的 SQL""跟着你的 schema 走的类型"都在命名一种感觉。修法是说出机制或一个数字:"`.toSQL()` 返回的就是发给数据库的那个字符串""改一个列名会让构建失败"。问一个句子告诉了读者什么可以做的事、可以知道的事,然后把那个写出来。如果改不成一条具体指令、事实或数字,就删掉它。再补一句检查:如果一个句子能原封不动地出现在另一个项目的文档里,它对这个项目什么都没说,删掉。
- **拆开密集的句子。** 读者要往回读才能解析一句,就拆成两句或砍掉从句。一句一个意思。
- **主动语态。** 抓到"is/are/was/were + 过去分词"就点出动作的发出者:"查询被校验"改成"编译器校验查询"。只有动作发出者未知或确实不重要时,被动才可以。
- **砍副词,或者换个更强的动词。**"跑得很快"改成"很快",或者直接给数字。"显著改善"改成测出来的差值。一个副词在撑一个弱的动词,说明动词选错了。
- **优先用普通的词。** utilize 换成 use,leverage 换成 use,facilitate 换成 help,numerous 换成 many。花哨的同义词很少更清楚。
- **别做作。** 有字面说法的地方不要用比喻和修饰:格言、为了效果而用的修辞片段、把代码拟人化、比喻性的动词。想说什么就说什么。
- **别过度压缩。** 省掉冠词、无动词的碎片、符号式简写、缩写,会让读者去解码而不是阅读。"解析器拒绝坏日期 → 退出码 2,不写"改成"解析器拒绝一个坏日期,退出码 2,什么都不写"。写完整的句子,带冠词和动词,把箭头和缩写补全。

## technical-writing

`technical-writing` 是一套分层的文档标准,用在 docs、RFC、readme、PR 描述、commit message 上。它的目标只有一句:一个疲惫的工程师在第一遍就能看懂。

它分四层,每层回答一个问题:这是什么类型的文档,句子怎么面对读者,每句承载多少,有没有句子能被读出两种意思。四层一起用。

四层之上还有三条总规则。用不上的词全删,"in order to" 就是 "to"。用短而日常的词,"use" 而不是 "utilize"。第三条约重要:当某条规则让一句话变差时,换个写法或者不动它。规则是为读者服务的,一句遵守了所有规则、却读起来像机器写的话,是失败的。

**第一层:先选模式(Diátaxis)。** 一篇文档只有一种模式。两个问题选出它:内容是在讲行动(doing)还是理解(thinking),是在服务学习还是工作。

- 行动 + 学习 = **教程**。你是老师,学习者的成功是你的责任。打开时说的是学习者要**做出**什么,不是他"将学到"什么。每一步都产出可见的结果,而且尽早、经常。告诉他应该看到什么:期望的输出、提示符的变化、那行日志。解释压到一个从句加一个链接。写成"我们",用命令:"先做 x。现在做 y。"
- 行动 + 工作 = **how-to**。解决一个人的问题,不是一台机器能执行的操作。假定对方有能力,跳过教学,只讲行动,不留离题、背景和为了完整的完整。用任务给它命名:"如何校准雷达阵列",不是"雷达阵列校准"。
- 理解 + 工作 = **参考**。只描述,不指导、不说服、不给观点。干、全、确定。把事实、选项、限制和错误平平地说出来,不 hedge。结构上镜像被描述的东西。尽量从代码生成,好让它保持真实。
- 理解 + 学习 = **解释**。一个有边界的话题,可以脱离产品单独读。标题都能承受前面加一个"关于"。锚在一个真实的 why 问题上。给上下文:设计决定、历史、约束、备选。只有在这里,观点是允许的。

不要把模式混起来:教程里不放参考表,参考里不做手把手的教学,how-to 里不辩论。混了就拆开、链接过去。

**第二层:把句子写给读者(Google 开发者风格)。** 用"你"、现在时。说清谁做什么:"编译器检查",不是"被检查"。指令写成命令:"点击 Submit。" 条件是前置的:"要删除文档,点击 Delete。" 常见情况放前面,例外放后面。不许预告("我们很快会支持……"),不要连续几句用同一个短语开头。链接要说清它通向哪里,永远不要"点这里"。标题要带出观点("先选模式",不是"模式"),用句子大小写。一页一个 h1,不跳级。

**第三层:让陈述一次承载一个(STE)。** 一条指令一个句子,其他地方一句一个念头。超过约 20 词的指令、超过约 25 词的其他句子,拆开。警告或条件放在它守护的那一步**前面**。保留"the"和"a":"移除备份文件"能读成两种;加上冠词只读成一种。每个词一个意思、一个职责,然后守住它。一个动作固定一个词:"start",不要这里 start、那里 initiate。流程写成直接命令,永远不写成叙述,也永远不用被动。尽量避开 `-ing` 词。

**第四层:不给句子留下两种读法(全球英语)。** 让"only""not"贴着它修饰的那个词。拆开长名词串。每个"it""they""this"都要指向一个明确的东西,拿不准就重复那个名词。不要省动词。保留显示结构的小词,比如"确保**那个**开关是关的"里的"那个"。in a series 重复冠词以防误读。说清"and""or"连接的是哪些部分。用句号,不用分号。把破折号换成一个新句子。括号里的内容要么是一个完整的语法单位,要么是它自己的句子。不用斜杠。每个东西自始至终一个名字。

它还有一条容易被忽略的:**让节奏有变化。** 一篇文档可以条条合规,却依然读起来像机器写的,因为每句话都被削得一样短,没有一个观点,没有一处具体。所以句子长短要有意地混合,短句落一个点,长句带一个事实和它的条件;在允许表达观点的模式里(比如解释),要说出你怎么看,而不是只列正反面。

用词上,代码库本身就是词表。写真实的符号、文件、flag、命令名,不要写它的同义词或描述。也不要用生造的术语,用开发者会脱口而出的词。名字不该造:说"move""delete""一个只会变小的预算",不说"evacuate""ratchet""endgame"。

最后一层分工:`technical-writing` 管文档,PR 描述和 commit message 也是写作,除 Diátaxis 之外每一层都适用;产品 UI 的文案不算文档,用产品自己的文案规范;而且它每碰一处文档,都要再过一遍 `unslop`。

## no-comments

`no-comments` 把注释交给一个**没写它的** reviewer,再处理被接受的发现。

为什么注释要单独走一遍,而且不能交给写它的那个 agent。原因很朴素:一个作者会像维护自己的东西一样维护自己的注释,你替我辩护,我也替你辩护。所以要换一双眼睛。

这个 reviewer 叫 Comment Sicko,只读,手上有一份很短的 keep 清单:license 头,公共 API 上的 doc comment,解释代码说不清楚的 why 的链接,以及由你无法改的外部依赖强制出来的行为。除此之外都走。你自己代码里蹦出来的意外,没有这种豁免。那条注释会作为一次重构信号回来。

它的步骤里有一条很细的分辨:**要把一次删除和一个错误判断分开。** 它检查 Comment Sicko 的报告和 diff,拒掉那些跑到应用代码里的编辑、越出范围的编辑、被例外条款保护的删除、写错了的"必须删"理由,以及把故意保留的代码当成有罪的标记。一个 keep 要活下来,必须带着"这是我们改不了的东西"的证明。对一个薄的"重要"或"不要删"的标记,它先跑一遍 `how` 或 `why` 去查那个符号;判断不了的时候,一个删除不恢复,一个 keep 被驳倒就删掉。

它的收尾动作很好。当一个注释声称一个约束,写着"不要删""不要改这段文案""改之前先问 X",`no-comments` 会提供一个把这个约束**编码**成类型、测试或 lint 的方案。要么编码它,要么删掉它。这其实是 encode-lessons-in-structure 在注释上的应用:一条约束如果值得写下来,就值得让某个东西去强制它。

分工值得记清楚。`deslop` 清代码里的 slop,`unslop` 清散文里的 slop,`no-comments` 把注释交给一个没写它的人。

## typescript-best-practices

`typescript-best-practices` 把 type-system-discipline 落成具体的语法规则。

它一开始就说明:**先应用 type-system-discipline 那条原则 skill**,它负责方向,这个 skill 负责语法。它的 frontmatter 里带 `paths: ["**/*.ts", "**/*.tsx"]`,所以当任务碰到 `.ts` 或 `.tsx` 文件时,要显式敲一下它才会进入上下文。

规则是一条条具体可查的。

- **可辨识联合。** 用一个 `kind` 字面量判别式建模变体,让非法状态无法表达。不要用可选字段的袋子。
- **品牌类型。** 用 `& { readonly __brand: "X" }` 给原始类型打品牌,让它们不能互换。在边界处校验一次。
- **构造式建模。** 把形状建成让非法值无法被构造。非空列表用 `[T, ...T[]]`,偶数长度用 `[T, T][]`,时间区间用 `start` 加 `duration`。不是运行时守卫,不是指望一个 refinement type。
- **最简单的全函数类型。** 只要上面的每个操作都保持全函数,就留着 `T[]`。只有松类型逼出 `!`、一个 cast,或一句"这不该发生"的 throw 时,才收紧成 `NonEmpty<T>`。
- **`unknown` 优于 `any`。** 外部数据是 `unknown`。
- **schema 先于守卫。** 在手写一个逐属性的类型守卫之前,先用仓库的运行时 schema 库,并从 schema 推出类型,比如 `z.infer`。
- **不用 `as`。** 每一个 `as` 都是一次等待发生的运行时崩溃。只在校验之后才 cast。
- **收窄的层级。** 判别式 switch > `in` 操作符 > `typeof`/`instanceof` > 自定义类型守卫 > `as`。
- **类型守卫必须真的验证它的声明。** 一个撒谎的守卫比 `as` 更糟,因为 bug 藏在一个说它安全的名字后面。命名成 `isX` 或 `hasX`。
- **穷尽性。** 在 default 分支里内联 `const _exhaustive: never = x;`,让编译器在新增变体时报错。
- **`satisfies` 优于 `as`。** 它校验值,又不放宽字面量类型。
- **边界校验。** 数据进来的时候把它解析成一个命名的领域类型,`Record<string, unknown>`(无论怎么拼写)到那个解析为止。内部信任类型。
- **从 schema 派生类型。** 在声明一个新 interface 之前,先想 `Pick`、`Omit`、`Parameters`、`ReturnType`、`Awaited`、`typeof`。
- **对象参数。** 传对象,不传位置参数,让参数顺序自解释。热路径跳过(每帧渲染、分词器、解析器)。
- **真实的测试。** 能跑的不要 mock。优先用框架真实的测试原语加泄漏和释放检查,UI 在运行中的构建里验证。只 mock 本地跑不了的东西。
- **结构化的遥测。** 优先用结构化日志诊断,带足够从一个 id 调出问题的上下文。发布代码里不留 `console.log`。

它还有一份 `references/patterns.md`,放具体例子。

## 把四个连起来看

这一组都在往外看,看的是"别人读你的产物"这件事。

`unslop` 管散文,`technical-writing` 管正式文档,`no-comments` 管注释,`typescript-best-practices` 把一条架构原则落进具体语言。它们的共同假设是:作者看不见自己的问题,所以需要规则清单,或者一个外部 reviewer。

边界也要说清。清洗不是可选的润色。一个带着叙述性注释和防御性死重的 diff,在 reviewer 眼里就是未完成,而且多出来的那部分代码,正是下一个 bug 藏身的地方。如果你自己都觉得这个 diff 有点撑,提交之前就清,别等 review 指出来。

## 今天就做一件事

提交之前,分三样东西清。代码走 `deslop`,散文走 `unslop`,注释交给一个没写它的 reviewer。三件事指向同一个结论:让不在这段代码里投入过感情的人来看一遍。
