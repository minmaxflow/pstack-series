# pstack 拆解 11 · 理解(上):它怎么运作

模型写出来的代码总是"看起来对"。第一件事,是看它现在到底怎么运作:数据从哪来、经过哪些形状、状态在哪里改变、失败时会发生什么。

## how

理解先于修改。一个系统真正的行为,只有被追踪过才知道:文档会过时,人的直觉会骗人,而 agent 失败的两大原因之一,恰恰是缺少足够的上下文把事做对。所以在动手之前先建立一份被追踪过的模型,是一项投资,它拦住的是第一次就改错地方。

`how` 回答"这段代码现在是怎么工作的"。

它产出的解释,停在资深工程师 onboarding 一个子系统的水平。够你建立可用的心智模型,但不会详细到像给源码加批注。输出有固定结构:概览、关键概念、它怎么跑、东西都在哪、坑在哪。

它的第一步是**判断复杂度**,这个判断决定了后面怎么跑。

窄问题走简单路径:一个 explainer,一次跑完,自己探索自己解释。大子系统走复杂路径:先并行起两到四个只读 explorer,每个负责一个角度,再把所有人的发现交给一个 explainer 合成。判断不了的时候,它走简单路径。

模型在这里有分工。explorer 是读和摘的活,用快模型;explainer 是理解和表达的活,用判断力最强的模型。

它也是被别人用得最多的一个 skill:investigation、bug-fix、feature、architect 都以它开头。
