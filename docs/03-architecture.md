# pstack 拆解 03 · Architecture

系统里有一条规则:订单一旦发货,就不能再改收货地址。

这条规则没有写在任何一个地方。它是七个 `if` 加起来的样子。每加一条新的下单路径,就要再补一个。三年后有人加了一条路径,漏了一处,于是已发货的订单被改了地址。

这不是粗心,是规则住错了地方。这一篇的六条原则都在做同一件事:**把规则从依赖人的记忆,搬进结构,让系统自己去守。**

还有一层背景值得点出:这批原则的内核是**函数式的**。函数式的世界观里,程序是“数据类型加函数”:类型要精确到“非法状态无法表达”,函数要尽量纯粹(输入决定输出,不碰外部世界),副作用挤到系统的边界;状态尽量不可变,能从别处推导出来的就不再存第二份。下面六条里,model-the-domain、type-system-discipline、boundary-discipline 是这套世界观最直接的体现,其余几条也在同一支上。作者本人有很重的函数式背景,这不是巧合。

## model-the-domain

领域建模的背后是这条原则最想让人接受的那句话:**程序等于数据结构加算法,而算法通常是平凡的,数据是核心。**

在业务系统里,真正复杂的不是计算,是领域本身:一个订单有哪些状态,状态之间怎么迁移,哪些组合根本不可能发生,谁在什么条件下能改哪个字段。这些规则一旦散落在条件判断里,系统就要求每个读到它的人都把这些规则在脑子里重新拼一遍,而且每加一条新路径,就多一个可能漏掉的地方。

把这些规则编码进一个数据结构,代码的性质就变了:它不再是需要你逐处小心的东西,而变成从模型里自然掉出来的东西。这是函数式编程最核心的一着:**代数数据类型(algebraic data type)**——用和类型把“要么这样、要么那样”的领域编码进类型,让非法状态无法表达,用结构消灭分支。

判断有没有做到,有一个很直接的信号:一个新功能是不是只是给已有的 if/else 又加了一支,或者又加了一个必须和另一个布尔保持同步的布尔。是的话,问题不在逻辑,在模型。

它有一句判据:**把领域编码进一个数据结构,而不是散落到各个条件判断里。**

原文为什么:写的时候选对结构很便宜,事后找回来就变成一次重构,而重构通常会被推迟。

它的做法是换结构。可以换成这些:

- 用状态机,替换散落的布尔、阶段和生命周期检查。
- 用带类型的对象或模型,替换松散的参数和重复的形状假设。
- 用 map、registry、查找表、可辨识联合,替换散到多个文件里的分支。
- 用 reducer 或命令事件模型,替换临时的状态修改。
- 用围绕一块领域知识组织的模块,替换"加载、校验、转换、保存"这种按执行顺序命名的模块。执行顺序不等于归属。
- 用队列、缓存、索引、图或规范化集合,来匹配真正的访问方式。

它同时刹车:不要硬塞抽象。如果当前的形状已经清楚、局部、且不太会长大,就选无聊的代码。对一个只增加间接、却不删分支和重复规则、也不消除非法状态的抽象,保持怀疑。

按执行阶段命名模块是另一个信号,它会在每一步里重复同一套领域规则。

## boundary-discipline

边界纪律的背后是函数式架构里那条很实用的分层:**功能核心加命令外壳(functional core, imperative shell)**。 不纯的东西,IO、校验、框架接线、网络,都被挤到系统边缘那层薄壳里;系统的核心留成纯函数,可以脱离框架单独测试。

它还有一个更精确的说法:**解析,不要校验。** 在数据穿过边界的那一刻,把它从无类型的原始形态一次性解析成领域类型;进去之后,代码只信任类型,不再到处加防御性检查。散落各处的校验之所以不好,不是因为它们多余,而是因为它们给出一种虚假的安全感,同时让业务逻辑和框架绑死在一起。

它有一句判据:**校验、类型收窄、错误处理,放在系统边界上;系统内部无条件信任。**

原文为什么:把逻辑从框架的接线里拿出来,才能不依赖框架地测它。

它的做法是按位置分三层。

**在边界上**(CLI 参数、配置文件、外部 API、网络协议):校验,返回错误,防御性处理。

**在系统内部**:带类型的数据,错误向上传播,不重复校验,信任类型。

**跨边界时**:暴露领域概念,不要暴露边界自己的私有表示。通用机制留在里面,特殊策略放在边缘。

几个具体的落点。配置在解析时校验(那是边界),不要在业务逻辑里校验。原始数据在边界就解析成领域类型。不要把传输层、存储层、框架、wire 类型从公共接口再导出去。边界已经校验过的数据,不要在调用链深处再加一次多余的 nil 检查。

它的检验有两个问题。这份数据此刻正在穿过系统边界吗?不是的话,校验是冗余的。这能不能是一个纯函数,让外壳只负责调用?能的话就抽出来。

## type-system-discipline

类型系统纪律的背后,是把正确性从运行时往前挪到编译期。类型系统在这里的角色不是"标注",而是一种**轻量的形式化方法**:你写下类型,它替你检查,凡是它能证明不成立的东西,就进不了生产。它用很低的成本,拿到了形式化验证里最有用的那一部分。

它的核心工具是让非法状态无法表达:用和类型、品牌类型、穷尽匹配,把一整类 bug 从"运行时可能发生"变成"编译不过"。判断标准也很直白:如果你的类型还允许写出一个没有意义的字段组合,那类型就太松了。

它有一句很好的话:**类型检查器是一个证明助手。**

总和类型、全函数、穷尽匹配,这些都是函数式语言的基本工具。这个原则把它们借了过来,不管你用的是哪种语言。

这个原则本身是语言无关的。每种语言的具体写法,放在对应的语言 skill 里,比如 TypeScript 的就在 `typescript-best-practices`(第 09 篇)。上面那句在 TS 里长什么样,那边列成了可查的表。

用它把三类东西在编译期消掉:不可能的状态、对不上的原始类型、没处理的变体。原文还有一句:一个类型让你能忽略的情况,会变成编译器本可以拦下的运行时故障。所以宁可把错误和特殊情况定义得不复存在,也不要增加一堆处理分支。

它的做法。

**让非法状态无法表达。** 用和类型建模变体,不要用一堆可选字段,因为矛盾的组合会通过编译。一个微妙的反例是 `{ completed: boolean; completedAt?: Date }`,它允许 `completed: true` 同时 `completedAt: undefined`,这个组合没有意义。要么从一个来源派生布尔,要么显式建模 `{ kind: 'open' } | { kind: 'done'; at: Date }`。如果你需要写一句注释解释"这组字段什么时候才合法",类型就太松了。

**类型是构造,不是限制。** 从你想要的值把类型建出来,而不是从一个更宽的类型用检查切出来。非空列表是"一个头加一个尾",不是"一个带长度检查的列表"。合法的时间区间是"起点加时长",不是"两个需要保持有序的时间戳"。选一个无法被构造成非法值的形状。

**给语义原始类型打品牌。** `UserId` 和 `OrderId` 底层都是字符串,但不该互换。

**外部数据在被解析之前是无类型的。** RPC 载荷、JSON、IPC 消息、CLI 参数、配置、环境变量、数据库行,每个边界一个解析函数。

**不要对类型系统撒谎。** cast、unsafe coercion、绕过编译器的断言函数,都是潜伏的运行时崩溃。编译器证明不了的事实,要么去证明它,要么承认这个 cast 是隐患。

**穷尽匹配是编译器的工作。** 加一个变体却没处理,编译就必须失败。

**从权威 schema 派生类型。** proto、OpenAPI、GraphQL、数据库迁移、设计 token,从它派生,不要手写一个平行的类型。

**只在完整性出现裂口的地方加强类型。** 运行时的断言、null 检查、"这不该发生"的 throw,都标记了类型太弱的地方。把那个检查推进类型里,然后停。类型系统的工作是追踪每个使用点必须处理的情况,不是尽可能精确地描述数据。

## make-operations-idempotent

幂等操作的背后是一个关于运行环境的现实:命令、生命周期步骤、处理循环,都跑在一个崩溃、重启、重试是常态的世界里。既然"只执行一次"这件事你保证不了,那就把正确性从"执行次数"挪到"终态":不管跑几次、从哪里开始、上一次在哪一步崩的,最终都收敛到同一个结果。这是把不确定性挡在系统外面的设计。

它有一句判据:**让操作收敛到同一个终态,不管它跑了几次,也不管它从哪里开始。**

它的做法。启动时收敛:扫描已有状态,清理过期产物,接管还活着的会话。清理按内容等价判断,不按创建顺序。锁能自愈:PID 判断过期。调度幂等:失败的工作干净地重生,每个周期后重新生成新输入。

它有三个检验问题。这个操作连着跑两次会怎样?上一次在每一个可能点崩溃会怎样?重执行会收敛到同一个终态吗?任何一个答案是"取决于留下了什么状态",这个操作就需要一个 reconciliation 步骤。

## migrate-callers-then-delete-legacy-apis

迁移调用方再删旧 API 的背后是一个判断:**双路径是复杂度的根源。** 一个系统要演化,本该是替换,但默认的惯性总是并存,因为并存最省事。并存之后,每个读者都要同时理解新旧两套,每处改动都要考虑两条路径,而旧路径因为"还有人在用"永远删不掉,代码库于是变成只增不减。

这条原则把清理当成演化本身的一部分:认定新设计是对的,就在同一波里迁移调用方、删掉旧 API,不给兼容层留活口。它只在三个前提同时成立时才用:没有外部用户依赖向后兼容,项目能承受一次协调的破坏性变更,新设计属于一次简化或重构。

它有一句判据:**当我们认定新 API 是对的设计,就在同一波里迁移调用方、删掉旧 API,不要保留兼容层。**

在满足前提时,它的规则很硬。不要因为内部调用方还在就保留旧路径。盘点调用方,迁移它们,立刻删除旧 API。临时适配器是例外,要限时,不是默认架构。测试更新成断言新契约,删掉那些只保护重构前实现细节的测试。

## separate-before-serializing-shared-state

先分离再串行的背后是一个被反复验证的结论:**共享可变状态是并发问题的根。** 当两个 actor 同时读写同一份状态,race condition 就出现了,而且它间歇、难复现、调试昂贵。加锁看起来是标准答案,但它只是把共享强制成串行,代价是复杂度和性能。

更好的做法是先问一个更前面的问题:这两个 actor 真的需要同一个可变对象吗,还是在发布各自独立的事实。多数情况是后者,那就让各自拥有自己的状态,只在读取和报告的边界合并,共享根本不存在。所以"我们需要一把锁"应该被当成一个要检查的设计味道;而且有一条很硬的话:指令和约定不是并发控制。

它有一句判据:**当并发的 actor 可能共享可变状态时,先问他们是否真的需要同一个可变对象。不需要,就消除共享;共享是真的,再用结构强制串行。**

它的做法分三步。

**先识别共享可变状态。** 双方都读写的文件,双方都推的分支,双方既定义又消费的 API。

**默认消除共享写目标。** 问一句:这些 actor 需要一个规范对象,还是在发布各自独立的事实?答案通常是后者。给每个 actor 自己的文件、key、分支、状态目录,只在读取和报告边界合并。这里有个容易混的地方:两个 worker 往同一个 `state.json` 写各自的 `lastX` 字段,仍然是共享变更;而 `indexer-state.json` 加上 `metrics-state.json`,就不是。

**只有当"一个共享写目标"是真实不变式时,才用结构强制串行。** lockfile、顺序阶段、单写者 actor、原子的 compare-and-swap 都算。而且要把"我们需要一把锁"当成一个需要检查的设计味道,不是默认答案。

## 把六条连起来看

这六条都在把规则从"靠人记得"搬进"结构强制"。只是搬去的地方不同。

model-the-domain 把领域规则搬进整体结构。boundary-discipline 把校验搬去边界。type-system-discipline 把约束搬进类型。make-operations-idempotent 把重启安全搬进操作设计。migrate-callers 把"只能有一条路"搬进迁移过程。separate-before-serializing 把并发下的所有权搬进状态划分。

有两组关系值得留意。

boundary-discipline 和 type-system-discipline 是一对。一个决定校验在哪里发生(边界),一个决定约束用什么表达(类型)。两者合起来,系统内部就可以完全不设防。

model-the-domain 是更上面的一层。它先选整体形状,后面几条都在这个形状里填细节。如果整体形状错了,边界和类型只能补救局部。

边界也要说清。这些原则都要求规则能被结构表达。有些规则是判断,结构表达不了,那就把它写下来,并且想办法让它至少被某个检查碰到。别为了用类型,把一个判断硬塞进类型里。

## 今天就做的一件事

动手之前,先问一句:**这条规则现在住在哪里?**

如果答案是一个人的脑子里,或者几个散开的 if 里,那第一个决定不是写逻辑,是决定它该住进哪种结构。领域规则进结构,校验进边界,约束进类型,重启安全进操作,并发所有权进状态划分。
