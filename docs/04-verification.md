# 04 · Verification

agent 报告完成了。CI 是绿的。你手动点了一下,功能是坏的。

它没有说谎。它只是把"能编译"和"测试通过"当成了证明。而这两样都不是。

这一篇回答 pstack 里最重的一个问题:**什么才算证明。**

它也是整个 pstack 的承重柱。guide 里有一句原话:验证是大多数 agent 工作里最慢的一步,因为它通常在等一个人。让 agent 自己会做,你就不再是瓶颈;跳过它,跑更多 agent 只会得到更多没人检查的产物。后面的委托、并行、自主,全都建立在这一篇上。

验证有五个形态,分别管五件事:看真的东西、修在真的地方、什么时候算可以往前走、测试有没有在观察行为、数字是不是在说你以为的事。

这一层背后有一个贯穿全系列的想法:**生成和评判必须分开。** 原因不是礼貌,是结构性的:一个模型审查自己刚生成的东西,带着系统性的偏见,它会偏好自己的输出,也对自己看不见的盲区最自信,而那些盲区恰恰是它犯错的来源。让生成者评判自己,等于让它的偏见同时充当标准。所以凡是重要的判断,都由一个没参与生成的一方做。这个想法在后面的 arena 的 cross-judge、interrogate 的多模型评审、shipping 里"判断改动的人永远不是写它的人"里反复出现。理解了它,你就理解了为什么 pstack 到处在制造"独立的一方":独立不是流程洁癖,而是因为不独立,评判就几乎没有信息。

## prove-it-works

证明它能用的背后是一个认识论上的区分:一个判断要对应世界上的事实,不能只对应一个模型。agent 的自述是模型对自己输出的信念,文件修改时间是一个变更的代理,缓存截图是某一刻的代理;这些都可能在真实情况已经错了的时候,照样显得合理。所以它要求直接观察真实产物。这会带来两个很实用的推论:验证失败时,先怀疑观察方法,再怀疑系统;而当某件事过得"太容易"时,也要先怀疑观察方法,因为一次错误的观察和一次真实的成功,在你眼里是一样的。

它有一句判据:**对真实产物直接检查,不要从代理、自述或"能编译"推断。**

原文为什么:没验证过的工作,正确性未知。间接验证(文件修改时间、输出新鲜度、agent 的自述、缓存的截图)看起来比直接观察便宜,但据一个错误的推断行动,代价远大于去查源头。

它的做法分两层。

**检查真的东西,不是代理。**

- 直接检查进程是否活着,不要通过派生出来的状态。
- 读真正的值,不要读缓存或二次表示的副本。
- 验证失败时,先怀疑观察方法,再怀疑系统。

**能脚本化就脚本化。** 最强的证明是一个确定性脚本,它重复同一个比较,不是一次性的肉眼看。写脚本,跑它,把输出留成 reviewer 能重跑的产物,而不是相信你的话。

还有一条关于产物的规矩。默认把产物留给人类,但只有大而复杂、以后需要审计的工作才提交它,比如一次大的移植或迁移。日常的小改动,让它可见就好,不必入库。

## fix-root-causes

修根因的背后是因果推理本身:症状和原因是两件事,而人天然会停在第一个说得通的地方。修症状会立竿见影,但每一次 workaround 都让系统更难推理,而真正的 bug 还在;时间一长,系统就变成一堆互相遮蔽的补丁。所以它把调试当成科学实验:先复现,形成候选假设,用运行时证据一个个排除,直到只剩那个能解释全部现象的机制。这里有一条特别实用的经验,是关于"重启类问题"的:先怀疑状态,再怀疑代码,因为持久化的脏状态,是最像随机的那类症状。

它有一句判据:**调试时不要修症状,把每个问题追到根因,在那里修。**

原文为什么:症状修复会累积。每个 workaround 都让系统更难推理,而真正的 bug 还在。根因修复前期慢,但能减少总的调试时间。

它的做法。

**先复现。** 没复现就不要谈修复。

**一直问为什么,直到根因。** 不要停在一个说得通的地方。

**不要加 guard。** 加一个 nil 检查让崩溃静音,就是修症状。

**如果一个 workaround 需要用一段话的注释来解释,那代码是错的。** 修代码,不是修注释。

**检查模式,而不只是这个实例。** grep 同样的模式,把所有实例一起修掉。

**卡住就插桩,别猜。** 加日志,读真正的错误。

它还有一条专门针对重启类 bug 的:先怀疑状态,再怀疑代码。持久化的状态,配置、缓存、锁文件、序列化的数据。如果清掉一个状态文件就恢复正常,那优先把状态校验当作修复。

## sequence-verifiable-units

把工作排成可验证的单元的背后是局部化:在造成破坏的最小单元上抓错最便宜,而在它之后才抓到的 break,定位成本不是线性的,是复利的,因为那时你已经在坏的地基上继续建了。所以它把二分法的原理用在开发节奏上:每完成一个小单元就检查一次,出错就能被锁定在这个单元里。交付层面是同一个道理的另一面:一串有顺序的 commit 本身是一个论证,先失败测试后修复,先基线后改动,先脚手架后功能,读的人不用相信你,看它先红、再看到它绿就够了。

它有一句判据:**把工作排成一串小单元,每个单元结束在一个可检查的状态,当前单元绿了再往前走。**

原文为什么:在造成它的那个单元上抓到的 break 很便宜。等到一批之后才抓到的 break 被埋起来了,而且你已经在坏的地基上继续建了。把这些同样的单元排成 reviewer 能重放的交付,就把"信我"变成"看它红,再看它绿"。

它有两个面,执行和交付。

**执行。** 在 sweep、migration,或者任何一串相似编辑里,每改一个就验证,再开始下一个。每个单元是一个前后括号:已知良好状态,一次改动,跑检查,继续。先 rebase 到干净的 trunk,让每次检查对着真正的基线。当杠杆替你做了编辑,每个单元的检查几乎免费,但仍然要跑,因为免费不是理由,证明才是。

**交付。** 按能证明工作的顺序堆 commit 和 PR。最典型的形状是失败测试在前,修复在后。别别的故事顺序也成立:重塑之前先做一次减法,治疗之前先捕获基线,功能之前先搭脚手架。每个 commit 单独可落地,整串读起来像一个论证。

## test-behavior-not-implementation

测行为而不是测实现的背后,是关于测试是什么的定义:测试是行为的规格,不是实现的镜像。一个只断言调用关系的测试,实际上是一台"变更探测器",你一改实现它就叫,但它并不区分"改坏了"和"改好了",于是它花掉 CI 时间和 review 注意力,换来的却不是缺陷探测能力。所以有一个很聪明的检验:如果这段代码 import 的每个函数都返回 undefined,这个测试还过吗;如果还过,它就什么都没观察,不可能因为缺陷而失败。这种测试该重写,或者删掉。

它有一句判据:**测试像用户那样调用代码,断言用户观察到的结果,对一个字面的期望值。**

它有一个很聪明的检验。留一个测试之前问:如果它 import 的每一个函数都返回 `undefined`,这个测试还过吗?如果还过,它就没有观察任何行为,不可能因为缺陷而失败。那就重写断言,或者删掉它。

原文为什么:一个不能为缺陷失败的测试,花掉 CI 时间和 review 注意力,什么也没抓到。而且常量钉子还会在有人编辑常量或 prompt 时失败,于是它实际拦住的,是那次编辑。

有五种测试会在此检验下现形,它们在被 import 的函数全返回 `undefined` 时仍然通过。

- 弱断言,或者没有断言。
- 只测 mock,或者只测"没发生"。
- 自指,期望值来自被测代码本身。
- 常量钉子,断言复述一个手工维护的常量或 prompt 字符串。
- fixture 断言 fixture,断言读的是测试自己造出来的数据。

修法是:用具体输入在测试体里调用被测对象,断言字面输出或可观察效果。要断言"没有",就在同一个测试里对另一个输入断言"有"。要测一个常量,就测读它的那个机制,用一个输入,而不是复述那个值。要测一个 mock,就断言它收到的载荷或调用之后的状态,而不是断言它被调用了。

有两类测试要保留:一张表的行和另一张表的行之间的关系测试,以及 `*.test-d.ts` 里的编译期检查。

## explain-the-number

解释这个数字的背后是测量的有效性:一个数字是一个关于系统的声明,而声明可以是真的,也可以只是看起来是真的。一次跑坏了的运行照样会打印一个合理的数字,因为失败的请求、被缓存跳过的工作、从没真正跑过的代码、没调优的一侧、以及 run-to-run 的噪声,都会产生看起来没问题的结果。所以拿到数字的第一件事不是用它,是先问它到底测了什么。这里最有用的一问是"为什么不是翻倍":如果你说不出是什么限制了这个结果,你还没有理解你测的东西。

它有一句判据:**在你信任、报告或据以一个数字行动之前,先找出什么限制了它,并排除它测的是别的东西。**

原文为什么:一次跑坏了的运行照样会打印一个看似合理的数字。失败的请求、跳过了工作的缓存、从没真正跑过的代码、两边设置不一致、run-to-run 的噪声,都会产生看起来没问题的结果。如果你说不出"它为什么没有翻倍",你就不知道你到底测了什么。

它的做法。

**问"为什么不是翻倍?"** 说出那个限制结果的资源或代码路径:一个核、一把锁、磁盘、网络,或者 load generator 自己。从 profile 或者运行期间的系统计数器得到它,再映射回源码。从读代码猜出来的不算限制。

**列出这个数字还可能测的是别的什么,每一项用证据排除。** 常见嫌疑是错误、跳过或被缓存的工作、没有调优的那一边、噪声、以及端到端里太小的那一块。

**把证据和数字放在一起。** run count、spread、limiter。性能数字就去走 benchmark-checklist 的整套流程,它把这条原则变成了七个要答案的问题。

## 把五条连起来看

这五条是验证的五个形态,各管一段。prove-it-works 管看真的东西。fix-root-causes 管修在真的地方。sequence-verifiable-units 管什么时候算可以往前走。test-behavior 管测试有没有在观察行为。explain-the-number 管数字是不是在说你以为的事。

它们合起来,给出一个可以自证的 agent。这就是那一根承重柱。

为什么它是承重柱。因为你没法信任一个不会自证的东西,而信任是后面一切的前提。没有它,委托就是把没检查的活转手,并行只会更快地产出没检查的活,过夜跑只会让没检查的活积累一夜。有了它,这三件事同时变得安全:你可以委托,因为你知道每一步都会被对着真东西检查;你可以并行,因为每个分支都能独立验证;你可以让它自主,因为完成与否由一个可检查的条件决定,不由它自己的说法决定。

边界也说清。验证不是万能的。有些工作没有廉价的可执行检查,这时候"不可复现"要如实报出来,`inconclusive` 不是 pass。最危险的失败模式不是没验证,是看起来通过了。

## 今天就做的一件事

在你说任何一句"完成了"之前,先回答一句:**这次用什么证明它?**

证明必须是一个别人能看到、能重跑的东西。一个脚本,一段命令输出,一个前后对比,一个写进去又被读回来的值。如果找不到这样的东西,那不是任务完成了,是任务还没到能给结论的阶段。
