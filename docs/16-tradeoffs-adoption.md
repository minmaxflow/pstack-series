# 16 · 取舍与上手

这套东西不是免费的,也不是到处都该用。这一篇收尾,讲三件事:它的成本,它的边界,以及你怎么把它变成你自己的。

## 成本

pstack 会在 subagent 和 review panel 上多花 token。这是 rigor 的价码,不是它的缺陷。

几个控制成本的办法。重跑 `/setup-pstack`,选一个更小的推理预算,或者更便宜的模型。一个很好的搭配是:主聊天用一个强模型,代码角色用更快更便宜的模型。把某个角色设成 `auto` 或 `inherit-parent`,让它在聊天自己的模型上跑。缩短 panel 列表,因为每一个 entry 会起一个 subagent。

最重要的一条:把 `poteto-mode` 留给需要 rigor 的工作。一个小的、一眼看穿的编辑,不需要走这一整条路。

## 什么时候别用

判断标准是可逆性和影响面,不是重要性。一个小而明显的编辑,你自己三十秒就能做完,还完全可控,让一整套 rigor 跑一遍并不划算。rigor 要花在难以反悔、影响面大的地方。

还有两个反直觉的使用习惯,值得单独说。

**不要在 prompt 里枚举 skill。** "先 /how,再 /architect,然后 /arena"这类写法,通常会把 playbook 已经排好的顺序打乱,或者漏掉它本来会保留的步骤。说清目标和约束就好。只有在你想覆盖某个具体选择时,才点一个 skill 的名字。

**先别说出你猜的原因。** 你说出的那个猜测,会把 agent 的搜索限制在你指的方向上。更好的顺序是先让它用自己的话重述问题,你从一个被误解的重述里,花一条消息就能纠正方向,而不是花一次错误的修复。

**别在任务中途改一个正在出问题的 skill。** 把它放进它自己的 PR 修,任务继续跑。一个混进功能工作里的 skill 编辑,对 review 不可见,也没法评估。

## 把它变成你自己的

poteto-mode 是某个人的风格。你可能不想要一模一样的那一套。

敲 `/automate-me`。它从你实际怎么工作里,把你自己的风格读出来,草拟一个 `<你的名字>-mode` skill,走审查流程,开一个 PR。你保留 pstack 做底,在旁边得到自己的路由 skill。

模型也可以配。敲 `/setup-pstack`。它检测你能用的模型,写一份很小的规则,把每个角色(code、judgment、各个 review panel)映射到一个模型。每个 skill 读它,没有规则时退回合理的默认值,所以你只覆盖你在意的那些。

有一个容易踩的坑要提醒。默认值变了以后,一条在变化之前写下的规则,会**继续钉住旧的默认值**。删掉那些角色行,或者删掉整个文件,再跑一次 `/setup-pstack`。

最后一条建议是:从比你想的更小的规模开始。你不需要第一天就有一堆 skill,甚至不需要整个 plugin。先朴素地 prompt,观察 agent 在哪里失败,当同一个失败出现两次,再加一个 skill 或一个检查。这和 encode-lessons-in-structure 是同一个循环:先让它痛,再把痛编码掉。

## 收束

这一整个系列,从头到尾其实只讲了同一件事:**可信。**

生成变便宜了。可信没有。pstack 把"可信"这件昂贵的事,拆成了 24 个名字,组织成能力,组织成程序,再交给一个调度器。它的目的,是让 agent 能自己对着一件真实的东西,证明自己的工作。

一旦这件事成立,后面的一切才安全。委托,是因为你知道每一步都会被对着真东西检查。并行,是因为每个分支都能独立验证。自主,是因为"完成"由一个可检查的条件决定,不由 agent 自己的说法决定。

反过来讲,如果跳过验证,跑更多 agent 只会更快地产生更多没有人检查的产出,而且这些东西的代价,会在你真正需要相信它们的时候一起到期。

## 最后一件小事

从明天开始,只做一件事。每次你或 agent 说"完成了"之前,先要一个证据。一个脚本,一段命令输出,一个前后对比,一个写进去又被读回来的值。

等你养成这个习惯,其余的都会自己长出来。你会开始想要原型,因为有些决定不该靠猜。你会开始想要杠杆,因为手工会重复。你会开始想要委托,因为你自己变成了瓶颈。你会开始想要底线,因为有些错不该犯第二次。

这些都不是从原则开始的。它们从一个很小的动作开始:**先要证据。**
