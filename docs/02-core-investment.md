# 02 · 基础、体验与探索

你把旧 API 手工迁到新 API。三百个文件,改了两天。合并上游改动时冲突了一轮,又重改一遍。改动本身没错,错在它是手工做的,而手工做的改动只能靠手工复核。

问题不在努力,在力气花的地方。这一篇的五条原则回答同一个问题:**力气该往哪里花。**

它们各自指向一个投入方向:定结构、为用户、探路、造工具、质疑前提。

## foundational-thinking

基础思考只有一句话:**先把核心的数据结构和类型定下来,再写逻辑。**

原文把这一点分得很清。结构决策保护的是未来的选择权,代码级决策保护的是简单性。这是两类不同的决定,不要混在一起。

为什么先结构。因为数据形状定对了,后面的代码会自己变简单;定错了,后面每个函数都在跟结构搏斗,而且越写越深。

它的细则。

**先数据结构。** 尽早定义核心类型,把每一种访问方式都走一遍,选出和主要路径匹配的结构。不要一边写逻辑一边改数据结构,那样每改一次都在还债。

**在代码层面,DRY 的是结构,不是每一行。** 类型和数据模型应当收敛,三句相似的话仍然好过一个过早的抽象。显式胜过聪明。

**并发推论。** 在两个 actor 之间共享状态之前,先问一句:如果另一个 actor 同时改它,会发生什么?只要答案不是"什么都不会发生",就隔离。

**先搭脚手架。** 如果某样东西让后面每一个阶段都受益,就先做它。CI、lint、测试基础设施、共享类型都是脚手架。排序为的是选择权:设置先于功能,测试先于修复。

**每个增量都落地一个连贯的抽象,或者加深已有的抽象。** 不要把一个新能力拆成一堆特殊情况,散到各个调用方去协调。

**减法排在脚手架之前。** 先清干净,再打地基。

落到一句检验上:数据结构定对了,下游代码会变得显然。如果你发现自己在写第六个特例分支,大概率是结构错了,不是逻辑不够多。

## experience-first

体验优先只有一句话:**当实现便利和用户愉悦冲突时,选用户愉悦。**

"用户"这个词要划清楚。对 UI,用户是最终使用者;对一个库或内部 API,用户是那个 import 它的同事;下一个维护这段代码的工程师也是用户。三类人都要算。

它的细则。

**每一项都要有理由。** 一个功能、一个控件、一个选项,如果说不清它为谁解决什么,它就不该存在。

**少而精。** 三个打磨到位的功能,胜过一个粗糙的十个。功能数量不是进度。

**先做原型再承诺。** 设计决策在扔掉的 HTML 里做,比在生产代码里做便宜得多。

**把细节做对。** 过渡、对齐、间距、反馈、错误状态,这些就是体验本身,不是收尾工作。

**收紧核心循环。** 每个功能要么服务于中心工作流,要么给它让路。

它和 foundational-thinking 的关系值得记住。原文有一句,基础应当服务于体验。基础思考管的是工作的顺序,体验优先管的是目标。一个决定先做什么,一个决定做到哪里算好。

## exhaust-the-design-space

穷尽设计空间只有一句话:**当正确答案不明显时,做两三个互相竞争的方案,并排比较,再决定。**

原文还有一句很关键:同一个形状的第二个口味不算数。你必须给出结构上不同的方案,否则那不叫探索,叫确认。

为什么值得。因为建错的东西,比探索三个方案贵得多。

什么时候用。代码库里没有先例的新交互,有多个可行路线的架构选择,体验取决于手感而不是逻辑的产品决策。

什么时候不用。已经有明确模式的机械实现,目标清楚的修 bug 和重构,约束只留下一个可行方案的时候。

这里最容易犯的错是"假装探索"。提出两个方案,其实是同一个思路的两种写法。真正的探索要能让你在结果出来之后改变主意,而结果是你眼睛能看到的原型或草图,不是你脑子里的对比。

仓库里实现这条原则的是 arena。它并行起 N 个候选,交叉评判,选一个做底,再把其他候选里最好的部分嫁接进来。

## build-the-lever

造杠杆只有一句话:**工作不平凡时,造那个做这件事的工具,而不是用手上做。**

它有两个回报,要分开看。

一个是吞吐。一个 codemod、生成器或脚本,每次都一样,还能免费重跑。

一个是信心。工具是一个 reviewer 能读、能重跑的产物。手工改的东西只能靠重做来复核。一个确定性的脚本,把"信我"变成"跑这个"。

它的细则。

**默认造杠杆。** 只有任务确实平凡,几处一眼看穿的编辑,才跳过去。

**第一个单元先手工做。** 用手工做掉第一个,学出配方,再造工具。然后重跑工具,和手工版本 diff,证明它是对的。让这个杠杆可以安全重跑。

**按工作挑形式。** 编辑用 codemod 或脚本,重复文件用生成器,分析用一条 dump 到 sqlite 的查询,验证用可重跑的检查。

**确定性杠杆胜过 fan-out。** 如果工具能一遍处理所有单元,就自己跑,不要派一堆 subagent 去做脚本能做的事。这句在原文里很反直觉,值得记住。

**派活时,把杠杆写成子 agent 都读的 skill。** 配方、验证契约、不要碰的边界,放在一个产物里,并且放在它们的写范围之外,免得它们悄悄改掉契约。

**它会产生一个文件。** 如果你引用了这条原则,diff 里却没有 codemod、脚本、生成器或委派 skill,那你就是没应用它。这是原文的自我检查,很硬。

**活得比会话长的杠杆,提交它。**

边界在"平凡"。门槛是平凡,不是重复。一次性的活也可能值得造杠杆,前提是杠杆恰恰是那个让工作可检查的东西。反过来,两行改动不要为它造框架。

## attack-the-premise

质疑前提只有一句话:**当两个或更多共享同一个前提的修复,在同一个关卡上失败时,该怀疑的是前提,不是这些修复。**

它对付的是"再修一次就好了"这个错觉。

理由很直接。每一个在共享前提下的失败,都是关于这个前提的证据。

它的细则。

**先把前提写下来。** 前提就是每个失败修复都假设的那一句。

**下一次修复之前做一次普查。** 按 actor 数不平衡。普查显示的是哪些 actor 持有不平衡,不是不平衡有多大。普查要写成可重跑的脚本,这里就用上了上一条 build-the-lever。

**读偏斜。** 如果每次跑都是同几个 actor 持有大部分不平衡,说明有东西在给他们分配这个角色。找出是什么在分配,那个分配就是下一个要追的"为什么"。

**移除不对称,而不是补偿它。** 轮换角色、随机化分配、或者把角色挪走,让没有任何 actor 每次都持有它。加一条返回路径、一个共享池、一次批量交接、一个周期性再平衡,这些做法都保留了那个分配,只是每次多做一道工。这里能看到 laziness 的影子:能移除的不对称,不要用补偿去盖。

停止条件也明确。前提没写下、普查没做出来之前,不要开始下一个修复。如果普查显示各 actor 很均匀,那前提就不是原因,去别处找,普查留着当证据。

## 把五条连起来看

这五条都在回答"力气往哪里花",但花的时间点不同。

foundational-thinking 花在最早,定结构。experience-first 定方向,力气要朝着用户。exhaust-the-design-space 花在决定之前,用原型探路。build-the-lever 花在执行时,把一次性的劳动变成可重跑的产物。attack-the-premise 花在反复失败之后,回头质疑大家默认的那个前提。

其中有两对关系值得留意。

exhaust-the-design-space 和 build-the-lever 是一对。一个在决定前花力气,一个在执行时省力气。两者都把信任变成可复核的东西:原型是看得见的证据,工具是可重跑的证据。

experience-first 和 foundational-thinking 是一对。原文说得很清楚,基础应当服务于体验。基础思考管顺序,体验优先管目标。别让顺序对了、目标错了。

边界也有两条。探索这条,当前提没有先例时用,已经有明确模式时别硬探。杠杆这条,门槛是平凡,不是重复,别为两行改动造框架。

## 今天就做的一件事

对任何一段不平凡的工作,先回答三个问题再动手。

1. 这件事里,哪些部分我可以做成一个可重跑的工具或脚本。
2. 有没有一个决定其实是在猜。那它就该先出一个原型,而不是先写实现。
3. 核心的数据结构定了吗。没定就先定它,别先写逻辑。

下一篇讲 Architecture:把领域装进结构里,把校验关在边界上,让非法状态无法表达,让操作可以重跑,以及在并发下先消除共享。
