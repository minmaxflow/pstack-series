# 14 · 连续性与维护

这一组处理的是"时间"。工作很少在一次会话里干净地开始和结束。它会被打断,被接手,被分成很多阶段,事后还会留下一堆需要清理的东西。

四个 playbook,两两成对。`session-pickup` 和 `pause-safely` 是一对,一个接续,一个挂起。`multi-phase-plan` 和 `worktree-cleanup` 是一对,一个规划长工作,一个回收它留下的东西。

## session-pickup

`session-pickup` 处理恢复或接管一个新前 agent 在飞的工作。起手可以是一段 transcript,一个 cloud-agent 的 URL,或者一个推上来的分支。

它的核心立场是:**把之前的轨迹当作权威。** 它不重新推一遍,它读那段活的痕迹,重建分支状态和已经做过的决定,命名 resume point,然后验证继承来的声明对着原始目标还成不成立。

为什么要特意验证继承来的声明。因为一个"做完了"的总结,不一定等于它真的做完了。上一个 agent 可能记错了,可能用了一个已经不成立的假设,可能把一个未处理的边界当成了"以后再说"。所以 resume 的动作是:先信轨迹,再对着目标验证它。

它和我前面提过的 `recall` 是两件事。`recall` 重建你对一个话题的记忆。`session-pickup` 接管一段具体在飞的活。

## pause-safely

`pause-safely` 是 `session-pickup` 的补集。它干净地挂起在飞的工作,让它以后能被接续。

它触发于几种情况:你明确要暂停,你要下线,harness 要重启,或者上下文即将被压缩。最后一种容易被忽略,但很重要,因为一次压缩之后,当前的细节就淡了。

它的动作是把当前步骤做完或者干净地退出,提交一个 work-in-progress 的 checkpoint,再写一份 resume note。那份 note 就是下一次 `session-pickup` 的起点。

这一对合起来说明一件事:一个可接续的系统,必须显式地支持中断。中断不是失败,它是常态,所以它要有自己的处理流程,而不是靠运气留下一堆半成品。

## multi-phase-plan

`multi-phase-plan` 处理跨阶段或者跨堆叠 PR 的工作。

它的顺序值得记住:**先把剩下的开放问题用原型解决掉**,再写计划。它不写一份还没有代码碰过的抽象计划,因为那样的计划会把没验证过的假设固化下来。

然后每个 PR 写一节,每一节以"证明这次改动管用"结束。这里有一条很硬的判据:一个通过的测试套件不算那个证明。证明是要针对真实产物的,和验证篇里讲的是同一件事。

它还有一个边界。计划是**交付物**,它不实现它。它会在结尾点名下一个执行它的 playbook。计划写完之后,执行是另一个任务的开始。

它还有一个关于迁移的实用规则:把标准写进 prompt。比如"结果必须和原来完全一致,bugs included"。这一句防止迁移顺手修东西,否则新旧输出就没法比,等价这件事本身也就失去了意义。

## worktree-cleanup

`worktree-cleanup` 回收本地磁盘:清理已合并或已废弃的 git worktree,以及过期的 iOS 模拟器。

它的价值不在"删东西",在"安全地删东西"。它会按三个维度给每一个 worktree 分类:合并状态、有没有未提交的工作、还有哪些聊天仍然在碰它。只有证据允许清掉的才删,任何握有未提交工作的地方,它停下来等你的判断。

它是"隔离"这个做法的另一面。前面为了并行,给每个任务一个自己的 worktree;`worktree-cleanup` 负责那些 worktree 的退场。有进有出,一个长期用得下去的并行工作流才不会把磁盘和机器资源耗光。

## 把四个连起来看

`session-pickup` 和 `pause-safely` 是一对。一个接续,一个挂起。它们让中断变得便宜。

`multi-phase-plan` 和 `worktree-cleanup` 是一对。一个规划长工作,一个回收它留下的东西。它们让长工作变得可控。

这一组的共同假设是:工作会跨会话、跨时间、跨机器。既然会,那就把"接续"和"退场"都当成一等公民,给它们各自明确的流程,而不是指望一切顺利。

## 今天就做一件事

如果你今天要下线,而手上有在飞的活,别只是关掉。让 agent 走一次 pause,提交 checkpoint,写一份 resume note。明天你会感谢今天这五分钟。
