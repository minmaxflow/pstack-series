# 11 · 理解、诊断与技能元

Part III 讲 playbook。一个 playbook 是**程序**:它由 skill 编排而成,带一个任务形状、一串步骤、一份证据契约,还有一份完成和回复的契约。

它有一个很具体的执行约定:匹配上一个 playbook 时,poteto-mode 会把这个 playbook 的步骤**原样拷贝**进 todo list。一个你决定不做的步骤,不删除,留在列表里,标一条 `skip: <原因>`。所以你永远能看到它选择不做什么。

这一篇的五个 playbook 有个共同点:**交付物是答案、诊断或一次被验证过的 skill 改动,不是代码。** 它们背后的想法是:探索、诊断、修复、评估是四种不同的认知姿态,混在一起会互相污染。它们的价值,是防止"手比脑子快"。

## investigation

在弄清问题之前不要动手。理解一个问题的最好方式,是先让证据说话,而不是先改代码。

`investigation` 处理只读的问题。它回答三种问法:这是怎么运作的,它为什么被造成这样,我们确定吗。

它路由到 `how`。如果是关于动机的问题,再加 `why`。如果是几个选项之间做决定,它返回一个带权衡表的推荐,而不是一个解释。

它有一条很硬的性质:它是只读的,产出的是一个带引用的解释或推荐,不是一次代码改动。没有 PR,没有 babysit。只有一种情况例外,当这次调查是先于一次代码改动的前置,那时候它把结果交回给你,重新路由到 bug-fix 或 feature。它的 throughput checkpoint 只有一行:`n/a, read-only investigation`。

它最值得学的一点,是它逼你把证据和猜测分开。你在 prompt 里加一句"给我你用了什么数据",它就会把两者摆开。

有一个用法特别有效:当一个报告很嘈杂(一长串讨论、一个模糊的 bug),先做一次调查,让结论变成一次重述。

```text
/poteto-mode 读这段讨论。用你自己的话说清底层的问题是什么,用大白话。先不要改任何代码。
```

一个误解会在重述里现形,纠正它只花一条消息。而如果直接让它改,一个误解会变成一次错误的修复。所以当成因不清楚时,先要发现,不要先要修复。

## runtime-forensics

症状和原因分开,诊断和修复也分开。混在一起,你就没法判断修复是不是对着真原因。

`runtime-forensics` 处理一个活着的症状:内存泄漏、空转的 CPU 占用、一个偶发的视觉 glitch。

它从插桩得到诊断。它遍历运行中的进程,加日志和计数器,让程序自己把状态说出来,而不是靠读代码推测。一个具体的 prompt 长这样:

```text
/poteto-mode 这里有一个很慢的启动。告诉我时间花在哪,哪些源码行拥有那些时间。先不要修。
```

它的交付物是一份诊断,不是修复。这个边界很重要。诊断和修复混在一起,你就没法判断修复是不是真的对着测出来的原因。先拿到诊断,再单独开始一次修复。

## trace-forensics

`trace-forensics` 处理一份事后交给你的 profiling 产物:cpuprofile、trace、spindump、heap snapshot。

它的活是读那份产物,把热点帧映射回源码。它也在这一步划清边界:交付物是诊断。你给它的是一份已经捕获下来的东西,它告诉你时间花在哪,哪些源码行拥有那些时间。

它和 runtime-forensics 是一对。一个从活着的进程出发,一个从冷冻的产物出发。前提一样:先诊断,再修。

## authoring-a-skill

面向 agent 的散文就是行为:一句含糊的话,会被某个未来的 agent 真的执行。

`authoring-a-skill` 是写或改一个 `SKILL.md` 的 playbook。

它有一句判断前提值得记:面向 agent 的散文,比面向人的散文门槛更高。因为一句没用的话,在这里变成的是某个未来 agent 会真的去遵循的指令。人的文档里一句含糊的话只是让人皱眉,agent 的文档里一句含糊的话,是行为。

它自己不放任你手写。它走 skill-authoring 的流程,校验 frontmatter 和链接,然后走 opening-a-pr。所以写一个 skill 也是一次有审查的正常改动,不是随手丢一个文件。这个约定本身,就是"skill 是基础设施"这个态度的体现。

有一个特例它单独处理。如果一个 skill 的职责是驱动你的应用并证明行为,那它是一个验证 skill,应该走 `create-verification-skill` 和 `maintain-verification-skill`,而不是普通的手写流程。

## eval

观察者效应:一个知道自己被评估的 agent,行为会不一样。所以测试必须是盲的。

`eval` 测的是一个 skill、结构或 prompt 的改动会不会改变 agent 的行为,在它被推广之前。

它整个设计围绕一个失败模式:**观察者效应。** 一个知道自己正在被评估的 agent,行为会不一样。所以候选 agent 拿到的是一个看起来有机的任务,放在被清理过的目录里,永远不出现 "eval" 或 "candidate" 这些词,也永远不知道彼此存在。一个 judge 用中立的标签给所有输出打分。而"有没有跟着链条做",从每个候选**实际读了哪些文件**来评分,不是从它自己声称的。

它有一条给你的规矩:接受判决之前,自己读一遍每一个输出。如果你不认同 judge,先怀疑 rubric,再怀疑自己的判断。

这说明一个 skill 改动不是小事。一次 skill 编辑影响之后每一个会话,所以在它被信之前,要像对待一个实验那样对它。反过来说,它也是"改一个 skill 之前先测一下"这件事的可执行版本,而不是靠一次坏会话的直觉去改。

## 把五个连起来看

这五个 playbook 的交付物都是答案、诊断,或者一次被验证过的 skill 改动,不是代码。

它们的价值在于防止"手比脑子快"。investigation 防止你在弄清问题之前就改代码。两个 forensics 防止你在找到原因之前就改代码。authoring-a-skill 和 eval 防止你在验证之前就改一个会影响所有会话的 skill。

边界在这一篇里反复出现,值得单独收一句。对抗性审查用在 diff 上,不用在计划上。诊断和修复分开,先拿诊断。eval 的判决,自己先读一遍输出再接受。

## 今天就做一件事

下次碰到一个"这是怎么回事"的问题,先走 `investigation`,让 agent 只给发现,不给修复。等发现指向一个确切的原因,再开一次新的任务去修它。
