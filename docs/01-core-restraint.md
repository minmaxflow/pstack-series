# pstack 拆解 01 · 决定与克制

你让 agent 给一个命令加一个 `--json` 开关。

它新建了一个 `JsonFormatter` 类、一个 `Formatter` 接口、一个工厂函数,把 `format` 参数穿过六个函数,顺手加了一个配置项。diff 有 400 行。评审花掉一个小时。两周后,有人发现文本输出被改坏了。

这一次,agent 每一步都没做错。它只是默认了一个动作:把能力加上去。没有人问过,这件事需要多少工。

这一篇的五条原则回答同一个问题:**这次改动该有多大。**

它们不是五条并列的规矩,是一条链:默认不做,做也先减,用读者的负担衡量少,需求变了就重画,迁移朝终态收敛。

## laziness-protocol

懒惰协议的背后是一个判断:**代码是负债,不是资产。** 每一行你写下的代码,不只是一个当下的解决方案,还是未来每一次阅读、修改、迁移都要重新付一次的成本。所以"写出来"和"有价值"是两件事:代码是达成结果的手段,它本身就是负债。懒惰协议的整个立场都建立在这个交换上:不追求少写,追求在结果相同的前提下,引入的复杂度最小。它衡量的单位是复杂度,不是行数。

它有一句判据:**用最小的代码和复杂度,拿到最大的结果。**

协议防的是后者。

反直觉的地方在这。agent 被要求"加个功能"时,默认动作是加。加一个类,加一层抽象,加一个参数穿过所有调用点,加完看起来就完整了。回到开头那个 `--json`,正确的第一步是先问一句:现在有几个格式化目标?一个。那就先不要接口。

它有六条具体的做法。

**优先删除。** 当你被要求重构或"改进"一段代码,第一个动作不是想加什么,是想能删什么。改进的默认方向是减法,因为每删掉一个概念,以后所有人都少记一件事。

**保持调用层级扁平。** 避免很深的调用链。这里有个容易混的地方:一个接口很厚、内部做了很多事,不叫深调用链。深调用链是 A 调 B 调 C 调 D,每一层都很薄,你为了追一个值要跳四次。判据很具体,回答一个问题如果穿过三个以上的文件或层级,就拍平它。

**集中决定。** 同一个选择不要在多个地方重复。把它放到唯一的事实来源,只把结果当一个简单的标志传出去。比如"要不要显示时间戳"这个决定,不要在每个消费者里各判一次,在边界判一次,传一个布尔下去。

**最小化 diff。** 用能解决问题的最小改动,更少的行胜过"优雅"的样板。这里的敌人常常是那种看起来更专业的写法:一个接口、一个工厂、一个基类,写出来很像回事,可问题只需要一个函数。

**质疑穿透。** 如果任务让你把一个新信号穿进类型、schema、管线这一层层结构里,先停下来,找一个更直接的路。穿透本身就是信号,它说明这个信号要穿过很多并不需要它的中间层,而这些中间层以后每次都要跟着改。

**处理小泄漏。** 纯转发的包装、把内部实现漏到外面的地方、重复的选择,在扩散之前清掉。小泄漏会复利成永久的协调成本。今天一个纯转发的包装,明天它长出一个参数,后天所有人都要绕着它走。

检验它只需要一句朴素的话:**如果一个人维护这段代码会觉得累,它就是坏方案。**

## subtract-before-you-add

先减后加的背后是一个观察:**系统不是一次设计出来的,而是一层层长出来的。** 每加一个能力,都会留下一点当时有用的结构,而其中一部分后来变成了没人敢动的噪声。等到你要再加东西时,你面对的不是最初的设计,而是设计加上所有历史残留。先减,就是先把这些残留清掉,让最初的结构重新露出来;在干净的表面上,下一步最好的设计常常会自己浮现。所以它是一个顺序问题:先减,后加。

举个具体的。你要给一段慢逻辑加缓存,先别急着加。去看它为什么慢,可能会发现半年前加的一个校验早就没人用了。删掉它,缓存根本不用加。

它的做法是这么几条。

**先把移除排进顺序。** 不要把清理留到最后当成收尾,它是前置动作。先让它变简单,再在简单的基础上盖东西。

**先砍,再打磨。** 先到最小可用,再往质量里投入。反过来做,你一边精修一边还在砍,精修的那部分很可能整个被砍掉。

**对着观察到的用法设计。** 为真实的调用方式建,不为猜出来的边界情况建。规格没要求的校验、解析器、守卫,先不动手。

**简化指令本身。** 重复的说明和过度的模板也是复杂度,删掉它们,读的人少记一层。

**没有新内容的引用就删掉。** 不要留一个空壳说"以后再补",空壳会被下一个人当成真的存在。

它背后是一个态度:把简化当成持续投资。你交出去的代码,表面应该不变或更小,能力不降。

## minimize-reader-load

降低读者负担的背后是一个事实:**一条代码写下一次,可能被读上百次。** 所以它真正的成本不在写的时刻,而在之后每一次有人要理解它的时候。可维护性不是一种风格,它是一笔可以被计量的工作量:读者要追上几层、要在脑子里同时记住多少东西。人的工作记忆是有限的,这和模型的上下文窗口是同一类约束,只不过一个在脑子里,一个在窗口里。把"下一个读者的代价"当成一等成本,是这条原则的全部出发点。

它有一句定义:**可维护性,就是读者理解代码要付出的工作。**

它只数两个维度。一个是层级,从问题到答案隔着几层。一个是状态,读者要在脑子里记住多少东西。这两个维度互相独立:一个 50 个全局变量的平铺文件,和一个六层适配器栈,一样难推理。

它的做法集中在两件事上,折层和缩状态。

**折叠得不偿失的层。** 只有一个调用者的包装、没有第二个实现的适配器、没被证明需要的中间层,这些都是纯成本。层只要它省下的理解成本少于它带来的,就该拍平。

**相邻两层必须改变抽象。** 如果一层只是把下一层的方法和参数原样再写一遍,它没有压掉任何东西,读者却要学两遍。这种只做转发的层直接删。

**接口要能压住复杂度。** 一个很宽、却藏不住复杂度的接口,会逼读者同时学表面和实现。好接口是藏住了一堆决定的那层薄壳。

**缩小状态范围。** 优先级是:纯函数好过变更,局部变量好过字段,字段好过模块状态,模块状态好过全局。能从一个值推导出来的,就不要存两份去同步,同步迟早会不同步。这是函数式的状态纪律:副作用越小、可变状态越少,读者要追踪的东西就越少。能推导就别存第二份,比如 `fullName` 能从 `firstName` 和 `lastName` 算出来,就别再存一个字段;存了就要保证它和两个来源一致,而它迟早会不一致。

**把不变式命名在边界。** 让读者在一个地方学会这条规则,而不是在每个消费者里重新推一遍。

加一层、加一份状态之前,先问一句:它在别处减少的读者负担,至少和它带来的一样多吗。

检验很干净:**一个新读者能不能在半分钟里回答两个问题,X 从哪来,什么能改 X。**

## redesign-from-first-principles

从第一性重画的背后是一个诊断:**系统往往不是被一次错误的设计毁掉的,而是被一百个各自合理的小补丁。** 每贴一块补丁,系统里就多住进一套局部逻辑:新的需求一套,原来的设计一套。补丁本身都没错,错的是它们让系统失去了"一个心智模型"这件事。所以整合新需求时,要维护的是设计的一致性,不是现状的延续性。"假设这个需求第一天就在,我会怎么建",是把设计重新拉回到一个模型上的办法。

它问的问题只有一句:如果我们是带着这个新需求从零开始写,会建出什么。

有个常见的例子。状态本来是个枚举,你要加一个"已归档"。贴的做法是加一个 `isArchived` 布尔,和原来的 `status` 并存。重画的做法是把它加进枚举本身。第一种两分钟写完,之后每个人都要问这两个字段谁优先。

它落到动作上是四步。

**先读全。** 把所有受影响的文件读完,先理解现在的设计是什么样,才谈得上重画。

**问那一句。** 如果从零写、带着这个需求,我会建出什么。

**让改动穿透。** 类型、文档、示例、设计理由,一个引用都不漏。漏掉的地方以后会以不一致的形式长回来。

**想完再分步交。** 先在脑子里完成整个重画,再把它拆成增量交付。不要一边想一边改。

它同时保住了未来的选择权。设计没有被补丁化,以后想换方向,路都还在。

## outcome-oriented-execution

朝终态执行的背后是一个关于债的判断:迁移和重写里最贵的代码,不是目标代码,是过渡代码。为了让每一步都不断档,你会写兼容层、双写、临时开关;它们本应该只活几次提交,却常常活成永久设施,因为没有人记得它们是临时的,而删掉又怕出事。所以优化的对象应该是终态:让系统朝一个可验证的终点收敛,允许中间态在计划内、有范围、可回退地坏一段。这需要先声明哪些破损是可接受的,再用一次完整验证收尾。

理由是:让每一个中间步骤都完全稳定,往往会产生临时兼容代码,而临时兼容代码会活成长期债。

一个具体的场景。把同步 store 迁到异步,为了不破坏现有调用方,你留了一层同步适配器。迁移宣布完成了,适配器还在,因为已经没人记得它是临时的。

它有个前提,别用错地方。它只适用于有明确阶段边界的计划性重写和迁移,不是随便一个改动都可以中途弄坏。

在满足前提时,它的规则是这些。

**终态完整性优先。** 目标架构是对的,比每一步都平滑更重要。

**先声明哪里可以坏。** 把临时破损的范围明确写出来,计划内、范围清楚、可以回退,这三条同时成立才算数。

**迁移期间保住高信号检查。** 对正在动的区域保留能报警的检查,别在过渡期把安全网撤了。

**完成时做完整验证。** 计划收尾时,做一次完整的静态和运行时验证,确保终态真的对。

检验方式:数一数这次迁移里有多少代码只为过渡存在,每一项都应该有一个删除日期。

## 把五条连起来看

这五条有先后。

先有"默认不做",才有"做也先减"这个排序问题。minimize-reader-load 给"少"定了单位,后面两条才有判据:重画的价值,在于把读者负担从两套逻辑降到一套。redesign 和 outcome-oriented 是同一个想法在两个尺度上,一个处理需求集成,一个处理迁移,都在拒绝补丁式共存。

但这不是说越小越好。build-the-lever 会让一次性的活也造个工具,因为工具是可被复跑的产物。exhaust-the-design-space 会让你故意建两三个原型。可检验性,或者没有先例,这两件事一出现,克制就让位。这是下一篇的主题。

还有一道更细的边界。minimize-reader-load 服务的是下一个读者,experience-first 服务的是使用者。两者都在优化别人的代价,但对象不同,别互相套用。

这几个名字在仓库里是活的接口。refactoring 拿 laziness 定最小改动的门槛,拿 minimize-reader-load 做验收。arena 打平时用 laziness 选边界更干净的那个。architect 推翻草图时先 subtract,再 redesign。attack-the-premise 在反复失败时选择移除不对称,而不是加一层补偿。

## 今天就做的一件事

动手前,先把这段发给 agent。

```
先别写。列出这次改动会新增的文件和抽象,每个写明谁会用它,以及你打算删掉什么。没有第二个使用者的抽象先不建。
```

写完再看三件事。

1. diff 里删掉了几行。零删除的改动,先解释为什么。
2. 从新入口到答案隔着几层。超过三层就拍平。
3. 有没有代码只为过渡存在。给每一项一个删除日期。

下一篇讲 Core 的另一半:先定数据结构,为体验而建,没先例就造原型,把工作做成杠杆,以及反复失败时质疑前提。
