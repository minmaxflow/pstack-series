# 06 · 理解

Part II 讲的是 skill。一个 skill 是一种**具名的能力**:它由若干原则组合而成,带一个明确的触发条件、一个固定的输出形态、一份契约。原则告诉你"什么时候该做什么",skill 告诉你"这件事具体怎么跑一遍"。

这一组 skill 处理的是信息问题。agent 失败通常只有两种方式:它误解了你要什么,或者它没有足够的上下文把事做对。第一种靠 prompt 解决,第二种靠这一组。

开篇那句可以说得很直:你不理解的代码,改它就等着出微妙的回归。这对 agent 和对人一样成立。一个没有追踪过模型的 agent,会在第一个看起来合理的地方修症状。

## how

`how` 回答"这段代码现在是怎么工作的"。

它产出的解释,停在资深工程师 onboarding 一个子系统的水平。够你建立可用的心智模型,但不会详细到像给源码加批注。输出有固定结构:概览、关键概念、它怎么跑、东西都在哪、坑在哪。

怎么用下一层,取决于问题的复杂度。窄问题,一个 explainer 一次跑完,直接探索加解释。大子系统,先并行起两到四个只读 explorer,每个负责一个角度,再交给一个 explainer 合成。判断不了的时候,走简单路径。

模型在这里有分工,explorer 用快模型去读和摘,explainer 用判断力最强的模型去合成。

谁在用它。investigation、bug-fix、feature、architect 都以它开头。

## why

`why` 回答"它为什么长成这个样子"。

它像一个查冷案的侦探。起点永远是源码历史,拿到文件和行,`git blame` 出最近改动的提交,从 merge commit 里抽出 PR 号。然后它去查你能接上的每一个证据类别,并行查:issue 追踪器、长文档、团队聊天、基础设施可观测性、错误追踪、分析数据仓库。每个类别一个 investigator,一个 MCP 对一个,全部同时发出。

为什么值得这么铺开。因为代码现在的形状,常常是很多早期决定一层层叠加的结果。只看最近一次提交会中 recency bias,而真相往往在更早的一次讨论里。

它的契约很讲究。报告引用一切,把直接证据和推断分开放,证据薄的地方就写"appears to"。空结果也要报,因为"没有人写下为什么"本身就是一个答案。

一个细节,investigator 要用 agent 模式而不是只读模式,因为只读会剥掉 MCP 访问,把靠 MCP 的调查员整个废掉。

## teach

`teach` 站在 `how` 和 `why` 之上,把两者织成一个朴素的解释。它的目标只有一个:让人真的懂,而不是让人收到一份摘要。

它有几条硬规则,值得单独记住。

先给朴素定义,用资深工程师在口头会说的方式把这个东西是什么讲清楚,再接到眼前的例子上,然后往上盖。给最小的完整答案先行,一两句,不要一上来就是密不透风的一段。

东西有三个以上活动部件时,不要画一张全图,画一串逐步叠加的图。每张在上一张上只加一个部件,让人看着系统自己组装起来。一张留到最后的全图是参考资料,不是教学。

不要打印框架标签。"关键洞察""核心要点""拿走的这一句",这类话一个都不要出现。直接说。

用具体机制,不用比喻。

这里还有一个和 `why` 有关的细节,`teach` 要原样保留 `why` 的置信语言。那些 hedge 是调查结论,不是文风。

它的用法里有一个值得偷的框:"convince me"。让 agent 说服你某个改动修的是根因不是症状,解释就从一次参观变成一场你可以戳的论证。

## recall

`recall` 把你自己的近期上下文重建出来。

它从你最近在这个工作区里的聊天,加上共享记录(issue、以前的修复、还在报的错误)里,拼出一份紧凑的简报:现在到哪了,下一步是什么。

为什么需要它。你的旧聊天里有新 agent 没有的上下文。开始一个旧话题的新工作时,先用 `recall` 把它载进来,再把新输入交给 agent。

有一个容易混的地方:如果你想恢复的是某一个具体的会话,那是 session pickup,不是 `recall`。前者接管一段在飞的活,后者只是重建你对一个话题的记忆。

## blast-radius

`blast-radius` 找的是一个改动可能在别处弄坏什么。

它有一个很关键的立场。列出调用方不是活儿,grep 十秒就有了。真正的活儿是 grep 看不到的那部分破坏:你调用的那个库的源码,它固定的版本,一个 API 返回的 JSON,一个数据库列,另一个语言读的同一段字节,一个 feature flag,下游三跳之后的代码。

它还有一条更重要的立场:一个听起来对的 blast-radius 分析,不管真假都同样有说服力。所以它不交论文,它找出"这个改动安全所依赖的那一两个事实",然后跑代码把它们证明掉。

信心分五级,尽量往低数字走,走到哪一级要说明。

1. 你这么说。单凭这个没有价值。
2. 你指出了那一行,给出真实的 `file:line`。
3. 你证明了坏情况到不了,一步步走过失败路径,它够不着。
4. 你跑了它。一个脚本或测试,调用真实的代码,如果你错了它会大声失败。
5. 你在运行的应用里复现了它。

通常一个很小的脚本就够了,它 import 应用发布时用的同一个库,调用你担心的那个函数。

它也是横向组合的例子:它会去调用 `how`、`why`,大改动时还会调用 `arena`,让多个模型回答同一个问题再合并。

## 把五个连起来看

`how` 管机制,`why` 管历史,`teach` 合成两者,`recall` 管你自己的上下文,`blast-radius` 管改动的影响面。前三个是认识一个系统,后两个是把自己和改动接进去。

它们组合的方式很固定。investigation playbook 直接以 `how` 开头,动机问题再加 `why`。bug-fix 用 `how` 给候选假设做种子,用 `why` 找回归史。architect 的 Phase A 用 `how` 打底,如果设计动了所有权,再加 `why`。

边界和陷阱就一条:不要因为"反正 agent 会读代码"就跳过这一组。一个没有追踪过模型的 agent,会在第一个看起来合理的地方修症状,`how` 跑在前面比第二次修 bug 便宜。

## 今天就做的一件事

在改一个你不熟的系统之前,先跑一次 `how`,让它把机制讲给你听。听完你觉得哪里不对,那正是你要先弄明白的地方。
